# 采购分册（业务用户手册）

> 覆盖模块：`/purchase`（采购申请、采购订单、采购退货）、`/srm`（供应商管理、供应商评估）。
> 通用约定见 [00-系统通用说明.md](./00-系统通用说明.md)。

---

## 1. 采购作业全流程图

```
需求提出 ──▶ 采购申请(/purchase/request) ──▶ 审批 ──▶ 转采购订单
                                                          │
                                   采购订单(/purchase/orders) 10 草稿 → 20 待审批 → 30 已审批
                                                          │
                                                    下采购单（用于下单）
                                                          │
                              ┌───────────────────────────┴──────────────┐
                              ▼                                          ▼
                  来料到货通知(/api/purchases/inbound-notify)   采购退货(/purchase/returns)
                              ▼
                     采购入库(/warehouse/inbound?source=purchase)
                              ▼
                  40 部分入库 ←→ 50 已入库（自动生成，不可手工改）
                              ▼
                       应付单(/finance/payable) + 付款(/finance/payments)
```

> ⚠️ **重要**：当前版本中，`采购申请 → 采购订单` 之间有一个**未打通的断点**（见 §2.4）。日常下单请直接走「采购订单」，或联系管理员用接口侧审批。

## 2. 采购申请 `/purchase/request`

列：申请编号 `request_no`、申请日期 `request_date`、需求日期 `require_date`、供应商 `supplier_id`、申请金额 `amount`、备注、状态。
另有「编辑 / 删除 / 批量删除」，接口 `POST|PUT|DELETE /api/purchase/request?id=`。

### 2.1 状态机（`PurBizStatus`）

| 码 | 中文 | 说明 |
|----|------|------|
| 0 | 暂存/草稿 | 新建默认，不入审批流 |
| 1 | 待审批 | 提交后进入审批流 |
| 2 | 已审批 | 通过后才能转采购 |
| 3 | 审批中 | 部分流程会写此值 |
| 9 | 已取消 | 取消后不可再提交 |

### 2.2 字段取值
- 采购方式 `purchase_type`：`1 招标 / 2 询价 / 3 直接采购 / 4 框架协议`
- 紧急程度 `urgency_level`：`1 普通 / 2 紧急 / 3 特急`

### 2.3 审批动作
- 状态为 1 时可执行 `approve`（通过）、`reject`（驳回）；
- /purchase/request/{id} 详情页有「批准」「驳回」两个按钮。

### 2.4 ⚠️ 已知断点（务必阅读）
当前界面上存在**三处与后端不一致**的地方：

1. **详情页的「批准 / 驳回」与列表页的「审核 / 驳回」目前只是前端提示「审批功能开发中」，并不会真正发请求。** 也就是说，采购申请在界面上无法被审批通过。
2. **转采购的链路是断的**：后端转采购接口要求申请状态必须是 `2 已审批`，但界面上没有任何动作能把状态推到 2（审批按钮不发请求）。因此**在界面上无法把采购申请转成采购订单**。
3. 单据状态口径存在两套并行的代码（旧的 `request_status` 与新的 `biz_status`），页面展示的是 biz_status，导出/统计口径可能不同。

**可行 workaround**：直接创建采购订单（§3）完成下单；确需走申请流程时联系系统管理员在服务端处理。

## 3. 采购订单 `/purchase/orders`

列：采购单号 `po_no`、供应商、采购日期 `order_date`、要求到货日期 `delivery_date`、总金额 `total_amount`、**状态** `biz_status`、审核人。

接口：`GET|POST /api/purchases`、`PUT /api/purchases/{id}`、`DELETE /api/purchases/{id}`、`POST /api/purchases/inbound-notify`（到货通知）、`GET /api/purchases/{id}/detail`。

### 3.1 状态机（`PurchaseOrderStatus`）

| 码 | 中文 | 谁来写 |
|----|------|--------|
| 10 | 草稿 | 新建默认 |
| 20 | 待审批 | 提交 |
| 30 | 已审批 | 审批通过 |
| 40 | 部分入库 | **系统自动**：采购入库按明细比例入库时写 |
| 50 | 已入库 | **系统自动**：全部明细入库完成后写 |
| 90 | 已取消 | 取消动作 |
| 99 | 已作废 | 作废动作 |

**业务规则**
- `40/50` 由入库收货自动推进，**不允许手工改**，改会导致库存与订单状态对不上；
- 只有 `20 待审批` 才能执行「审批」；审批通过后通常不允许直接编辑单价，需要变更请走「变更单」或先撤销审批；
- 取消/作废后单据进入终态，不能再执行入库。

### 3.2 采购明细
明细行字段：物料编码 `material_code`、物料名称、规格型号、单位、数量 `qty`、单价 `unit_price`、金额、需求日期、行备注。
数量/金额的合计口径为 `SUM(qty * unit_price)`。

## 4. 采购退货 `/purchase/returns`

列：退货单号、关联采购单、供应商、退货日期、退货类型、数量、金额、状态、备注。

| 动作 | 接口 |
|------|------|
| 列表 / 查询 | `GET /api/purchase/return` |
| 新增 | `POST /api/purchase/return` |
| 编辑 | `PUT /api/purchase/return` |
| 删除 / 批量删除 | `DELETE /api/purchase/return?id=` |

状态机（`PurchaseReturnStatus`）：`1 待审核 → 2 已审核 → 3 已退货`，取消为 `9 已取消`。
退货完成后会生成退货入库单并冲减应付，见财务分册。

---

## 5. 供应商管理 `/srm/suppliers`

列：供应商编码 `supplier_code`、名称 `supplier_name`、联系人、电话、地址、营业执照号、合作状态、创建时间。
操作：新增 / 编辑 / 删除 / 批量删除（`POST|PUT|DELETE /api/srm/supplier?id=`）。

> 供应商是采购单据的必选关联对象；删除供应商前请确认无未结采购单/应付。

---

## 6. 供应商评估 `/srm/supplier-eval`

列：供应商编码、供应商名称、评估期间、评分、等级、评估人、评估日期、备注。
操作：新增 / 编辑 / 删除（`POST|PUT|DELETE /api/srm/supplier-eval?id=`）。
另有「生成评估记录」动作 `POST /api/srm/supplier-eval/generate`。

评估数据存 `srm_supplier_eval` 表，指标维度：质量合格率、交货准时率、价格竞争力、服务响应、配合度。

## 7. 采购域常见问答

| 问题 | 说明 |
|------|------|
| 采购申请点了「审核」没反应 | 已知问题：审批按钮为占位，未真正提交；请直接建采购订单 |
| 采购申请转不了采购订单 | 已知断点：转采购要求 status=2，界面推不到 2；请直接新建采购订单 |
| 采购订单状态自己变成「部分入库/已入库」 | 正常：由采购入库自动推进，不要手工改 |
| 想改采购单价 | 已审批(30)的单建议先撤销审批再改；已入库(50)不能改 |
| 供应商删不掉 | 存在未结采购单/应付，需先取消相关单据 |
| 采购方式/紧急度选什么 | 常规补货选「3 直接采购」；比价/年度框架走「2 询价」「4 框架协议」 |
