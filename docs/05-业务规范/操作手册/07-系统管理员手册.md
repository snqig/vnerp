## 1. 日常巡检

### 1.1 巡检频次与项目

| 频次 | 检查项 | 怎么查 |
|------|--------|--------|
| 每工作日上班前 | 服务可访问性 | `curl -s http://<host>:5000/api/health`（返回含 `database`、`memory` 状态） |
| 每工作日上班前 | 昨夜备份是否成功 | `pnpm backup:list`，确认最新备份时间戳是今天 |
| 每工作日上班前 | 是否有锁定账号告警 | 见下方 SQL-A |
| 每周 | 慢查询 | 见下方 SQL-B（需先开慢查询日志） |
| 每周 | 事件积压 | 见下方 SQL-C |
| 每月 | 备份恢复演练 | 按 §4.3 在**非生产实例**演练一次并留记录 |
| 每月 | 离职/转岗账号清理 | 见 §2.6 账号生命周期 |

### 1.2 巡检 SQL

<details open>
<summary>SQL-A　异常账号（锁定中 / 已禁用 / 长期未登录）</summary>

```sql
SELECT id, username, real_name, status, login_fail_count, lock_time, last_login_time
FROM sys_user
WHERE deleted = 0
  AND (lock_time IS NOT NULL
       OR status = 0
       OR last_login_time < DATE_SUB(CURDATE(), INTERVAL 30 DAY)
       OR first_login = 1)
ORDER BY last_login_time;
```

`first_login = 1` 表示建号后还没改过密码，超过 3 个工作日仍未改密的，建议停用待本人确认。
</details>

<details open>
<summary>SQL-B　慢查询</summary>

```sql
-- 需先在实例上开启（生产建议 long_query_time = 1~2 秒）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 2;
SHOW VARIABLES LIKE 'slow_query_log_file';
```

对命中的 SQL 用 `EXPLAIN <原句>` 看 `type` / `key` / `rows`；若 `key` 为 NULL 且 `rows` 很大，就是缺索引。当前版本已为 20 张业务表补齐查询路径索引（`database/migrations/090_add_query_perf_indexes.sql`），升级后复核即可。
</details>

<details open>
<summary>SQL-C　事件总线积压</summary>

```sql
SELECT status, COUNT(*) AS cnt, MIN(create_time) AS oldest
FROM domain_event_outbox
GROUP BY status;
```

正常情况 `status='pending'` 应当接近 0（轮询器消费后转 sent/processed）。若 pending 持续增长且最旧记录不断被推后，说明消费端挂了，按 §7.4 处理。事件已处理记录另可用 `pnpm cleanup:events` 清理。
</details>

<details open>
<summary>SQL-D　数据库容量与连接</summary>

```sql
SELECT table_name,
       ROUND((data_length + index_length) / 1024 / 1024, 1) AS size_mb,
       table_rows
FROM information_schema.TABLES
WHERE table_schema = DATABASE()
ORDER BY (data_length + index_length) DESC
LIMIT 15;

SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
SHOW PROCESSLIST;   -- 找长时间 Sleep 与 Running 的连接
```

应用侧连接池默认 `connectionLimit: 20`、`queueLimit: 100`（`src/lib/db/index.ts`）。`Threads_connected` 持续接近 `max_connections` 时，先 `KILL` 掉空闲长连接，再查是否有接口在循环内逐条查库（N+1）。
</details>

## 2. 账号、部门、角色与权限

> 对应页面：**系统管理 > 用户管理**（`/settings/user`）、**系统管理 > 角色管理**（`/settings/roles`）、**系统管理 > 组织架构**（`/settings/organization`）。
> ⚠️ 历史 URL `/settings/users` 只是一个 `redirect('/settings/user')` 的占位文件，**已废弃**，请一律使用 `/settings/user`。

### 2.1 先把模型搞对：到底哪一处权限才真正生效

这是本分册最容易踩坑的一节。系统里有 **三套权限码词汇表并存**，它们长得像但作用完全不同：

| 位置 | 形态 | 是否参与服务端鉴权 |
|------|------|--------------------|
| `sys_menu.permission`（菜单表上一个 varchar） | 通配码，如 `orders:*`、`settings:user:*` | ✅ **这是真正生效的** |
| `sys_role.permissions`（角色表上一个 `json` 列） | 精确码数组，如 `["system:user","order:view"]` | ❌ **不参与鉴权**（列注释已明示） |
| `src/lib/permissions-catalog.ts` 的 `API_PERMISSIONS` | 代码常量池，168 条，界面「按钮权限」标签页勾选的就是它 | ❌ 只是 UI 展示与「按钮显隐」，服务端不看 |

> 📌 **2026-09-26 收敛说明**：三套里前两套（`sys_role.permissions` 与实际生效的菜单码）**必须一致才算授权完整**，
> 第三套（`API_PERMISSIONS`）与它们的偏差已由 `pnpm validate:permissions` 门禁卡住
> （也接入了 pre-commit 与 CI），改权限码时三处要同步。详见 `src/lib/permissions-catalog.ts` 的模块头注释。

用户拿到权限的真实链路（只读验证 SQL）：

```sql
SELECT DISTINCT m.permission
FROM sys_menu m
JOIN sys_role_menu rm ON m.id = rm.menu_id
JOIN sys_user_role ur ON rm.role_id = ur.role_id
WHERE ur.user_id = <用户ID> AND m.permission IS NOT NULL AND m.permission <> '';
```

代码侧对应 `src/lib/auth.ts:228-234` 的聚合查询。**结论：给角色勾「按钮权限」勾得再全，只要该角色没关联到带权限码的菜单（`sys_role_menu`），用户照样 403。**

### 2.2 权限生效链路与缓存

```
登录（POST /api/auth/login）
   → 签发 HS256 JWT（payload: userId / username / realName / roles[]）
   → 中间件 src/proxy.ts 验签（Bearer header 优先，access_token Cookie 兜底）
   → 接口 src/lib/api-permissions.ts 的 withPermission 比对权限码
   → 页面 src/components/auth/RoutePermissionGuard.tsx 收口菜单/按钮显隐
```

**权限改动不是即时生效的**，有一条 5 分钟的尾巴：

- 用户信息缓存在**进程内存**（`src/lib/auth-cache.ts`，TTL 5 分钟，上限 1000 用户）。
- 改完角色/用户后，系统会调 `POST /api/auth/cache/clear` 主动清缓存（保存角色权限时自动触发）。
- 但如果管理员**绕过界面直接改库**，就必须手动清缓存，或者直接重启应用。

> 排查「明明改了权限却没生效」的顺序：① 确认改的是 `sys_role_menu` 而不是只有 `sys_role.permissions`；② 让用户**退出重登**；③ 仍不行则调 `POST /api/auth/cache/clear`（需管理员令牌）后重试。

### 2.4 标准操作

#### 2.4.1 新增员工账号

1. 先在「组织架构」建好**部门**（父级别选错，部门树决定后续数据归属）。
2. 「用户管理 > 新增」填：用户名（必填、唯一）、密码（必填，**系统不生成**，自己定）、姓名（必填，会与 `sys_employee` 名单比对，对不上会被拦）、部门、角色。
3. 保存后系统自动把 `first_login` 置 1；该用户首次登录除白名单接口（改密、登出、菜单、个人信息等）外一律返回 403，**必须先改密码**。
4. 密码用 bcrypt 哈希存储（cost=10）。后端**不校验密码强度**，强度规则目前只存在于改密接口（最小 6 位、必须含字母与数字），建议在制度上要求 8 位以上。

#### 2.4.2 给角色分配权限（三标签页，一次保存）

角色管理页的权限区分三个 Tab，**保存时会连发三个写接口并清缓存**：

| Tab | 写哪儿 | 语义 |
|-----|--------|------|
| 菜单 | `sys_role_menu` | **全量覆盖**：先 `DELETE FROM sys_role_menu WHERE role_id=?` 再整批 INSERT |
| 按钮权限 | `sys_role.permissions` | **整列覆盖**：`UPDATE sys_role SET permissions=?` |
| 数据范围 | `sys_data_scope` | 先删后插，按「仓库 / 客户 / 供应商」三个维度勾选 |

⚠️ **「菜单」是全量覆盖，不是增量。** 界面上取消勾选某菜单，等于把该角色所有其他菜单之外的关联全部删掉；如果前端因为分页/懒加载没把菜单树一次传全，**漏传的会被静默删除**，表现为「某人突然打不开某个页面」。改完必须在测试账号上复验。

#### 2.4.3 重置密码

- **走界面**：用户管理里的重置密码会把密码置为硬编码 `123456` 并重置 `first_login=1`，用户下次登录会被强制改密。
- **走命令行**（忘记存了初始密码时）：

```bash
npx tsx scripts/reset-password.ts <用户名> <新密码>
```

⚠️ 该脚本**只改密码哈希，不撤销已签发的 token**。重置后旧会话仍然有效，需通知用户在其他设备重新登录。

### 2.5 现网部门基线（节选，2026-09 实测）

部门树为两层，`总经办(DEPT001, id=11)` 是根，下挂业务部(2)、工程技术部(3)、生产部(4)、供应链部(7)、品质部(9)、行政人事部(10)、财务部(16)；再由这几个部门往下挂科室，例如 `生产部(4) → 生产计划科(114) / 模切车间(5) / 商标车间(6)`、`财务部(16) → 会计科(122) / 出纳科(123)`。

新增部门请沿用 `DEPT` + 层级编码的规则（`DEPT00201` 这类），并在保存后确认父级正确。

#### schema 对齐说明（2026-09-26，P3-3）

- 修复范围仅限 `src/lib/db/schemas/system.ts` 的 `sysRole` / `sysUser`，**不改动线上 DDL**——库里这两张表的列本来就在，只是 Drizzle 定义漏了。
- 三处**类型漂移**一并纠正：`sys_role.data_scope` 由 `varchar(20) default 'self'` 改回库里的 `tinyint default 1`（否则会误导后来人「data_scope 是字符串枚举」）；`sys_role.description` 200→255；`sys_user.last_login_ip` 45→50。
- 新增列按库定义照搬、**没有顺手补外键**：`parent_id` / `create_by` / `update_by` 在库里只有索引没有 FK，补上就会与线上 DDL 不一致。
- 复核方式（只读，不连业务表）：对比 `getTableConfig()` 与 `information_schema.COLUMNS` 的列数与 `getSQLType()`，两张表现均为「列数相同、逐列类型相同」。
- 已知**未修**的漂移（本轮刻意不动，避免扩大改动面）：`sys_user` / `sys_role` 的索引名在库与 schema 里叫法不同（库是 `idx_department` / `idx_status`，schema 写的是 `idx_user_dept` / `idx_user_status`），且 `sys_user.department_id` 上库里挂了**两个**同名目标的外键（`fk_sys_user_department` 与 `fk_user_department`）。功能无影响，待单独排期。

#### 全库 schema 漂移治理（2026-09-26，P3-3 后续）

以「库为真相源」对 `src/lib/db/schemas/*.ts` 做了一次全量比对，并向 schema 侧收敛。**只改 schema，不动线上 DDL。**

| 项目 | 治理前 | 治理后 |
|---|---|---|
| 【schema 漏列】（库里有、schema 没写 → 走 Drizzle 写这张表会静默丢列） | 112 条 | **0** |
| 【幽灵表】（schema 定义了、库里没这张表） | 18 张 | **0** |
| 表定义总数 | 242 | 224 |
| `pnpm validate:schema-drift` 实质漂移 | 215 处 / 74 张 | **85 处 / 17 张** |
| 【schema 多列】（schema 里有、库里没有，涉及 17 张表） | 85 条 | 85 条（**本轮按约定未动**，属后续） |

- 漏列由脚本按 `information_schema.COLUMNS` 生成并补入，共 **469 列 / 27 个文件，纯新增 0 删除**；`decimal` 的 `.default()` 统一加引号（drizzle 0.45 只收 `string | SQL`），`enum` 映射为 `mysqlEnum('x', [...])`，未建模的列一律交人工而不是硬猜。
- 幽灵表 18 张（如 `sal_quote`、`eq_equipment`、`pur_order_deprecated`、`prd_work_order_color_seq`）在数据库里**确实不存在**，其 Drizzle 定义已删除；删除前逐张做了交叉引用与裸 SQL 引用核查。**删定义不影响业务**——本项目数据访问走手写 SQL，Drizzle schema 仅作类型定义层。
- 例外修正：`dcprint_tool` 库里同时存在 `deleted` 与 `is_deleted`，原来只建模了不存在的 `deleted` 指向、漏了真实的 `is_deleted`，已正名并补齐。

### 2.7 账号生命周期建议

| 场景 | 推荐动作 | 禁忌 |
|------|----------|------|
| 员工离职 / 转岗 | 改角色（转岗）或 **停用 `status=0`**（离职） | ❌ 物理删除。系统用软删除，历史单据靠 `create_by`/`operator_id` 追溯，删号会让单据变成"无名" |

## 4. 备份与恢复

完整脚本与参数见 **[04-运维指南/备份恢复.md](../../04-运维指南/备份恢复.md)**。此处只给管理员日常要记住的部分。

### 4.1 命令

```bash
pnpm backup           # 全量备份：mysqldump + gzip + SHA256 校验
pnpm backup:list      # 列出已有备份
pnpm backup:restore <file>   # 从备份恢复
```

### 4.2 备份策略建议

| 环境 | 频率 | 保留 |
|------|------|------|
| 生产 | 每日一次全量（周期由 `system.backup_cycle_days=7` 约束） | 近 30 天 + 每月末归档 |
| 重要操作前 | **手工额外备份** | 至该操作验收通过 |
| 演练 | 每月一次 | 记录到运维台账 |

**必须手工额外备份的场景**：月末结账、批量反审核/取消、批量删除、迁移执行、数据订正脚本、主数据合并。

```bash
pnpm backup && pnpm backup:list   # 记录本次备份文件名，写进变更单
```

### 4.3 恢复演练（每季度至少一次）

1. 用备份文件的**副本**在一台干净的实例上恢复，不要动生产库。
2. 起服务，验证：能登录、`SELECT COUNT(*)` 对得上几个关键表、最近一笔业务单据能打开。
3. 记录恢复耗时（应 ≤ 30 分钟）与失败点，写进运维台账。
4. 若未通过，立即停用备份自动化并通知负责人。

### 4.4 ⚠️ 恢复的硬约束

- 恢复是**整库覆盖**，`pnpm backup:restore` 前请确认已对当前库做备份。
- 应用**必须停服**再恢复，否则运行中拿到的旧连接池会写回新数据。
- 恢复完成后必须重启应用进程（连接池/内存缓存持有旧连接与旧用户缓存）。
- Docker 部署下 `docker compose down` 不删数据卷，但 **`docker compose down -v` 会清空数据卷**，禁止在生产使用。

## 5. 数据库迁移执行

完整流程见 **[04-运维指南/数据库迁移.md](../../04-运维指南/数据库迁移.md)**。这里给上线场景的执行 SOP 与踩坑清单。

### 5.1 命令

```bash
pnpm setup:db [--seed]   # 全新环境：建库 + 导入 schema + 可选种子
pnpm migrate              # 执行增量迁移 up
pnpm migrate:status       # 查看已执行 / 待执行
pnpm migrate:down         # 回滚最后一个迁移
pnpm migrate:create <name> # 新建迁移文件
```

### 5.2 生产迁移 SOP

| 步骤 | 动作 | 通过标准 |
|------|------|----------|
| 1 | 阅读迁移文件全文，逐条判断会不会碰到存量数据 | 无 `DELETE` 无条件语句、无 `DROP COLUMN` 未评估 |
| 2 | `pnpm backup` | 备份文件生成并校验 SHA256 |
| 3 | 在**预发/测试库**完整跑一遍 | `pnpm migrate:status` 与预发一致，应用能正常登录 |
| 4 | 窗口期停服，生产执行 `pnpm migrate` | 命令退出码 0 |
| 5 | 核对 `sys_migration`（列：`migration_name` / `batch` / `applied_at` / `execution_time`） | 本次迁移名已登记 |
| 6 | 起服务，抽样跑关键页面 | 无 500 |
| 7 | 跑 `pnpm validate:sql`（SQL 可执行性门禁） | `缺陷 0` |
| 8 | 观察一个业务周期 | 无新增错误日志 |

### 5.3 迁移踩坑清单

| 现象 | 原因 | 处理 |
|------|------|------|
| 迁移执行了但脚本没效果 | 未登记 `sys_migration` 后重跑会被跳过 | 见 `docs/04-运维指南/数据库迁移.md` 的登记纪律 |
| MySQL 报语法错误 near `ADD INDEX IF NOT EXISTS` | **MySQL 不支持该语法** | 本项目统一用 `information_schema.STATISTICS` 计数守卫 + `PREPARE/EXECUTE`（见 `database/migrations/090_add_query_perf_indexes.sql`） |
| 改了 DB 层/handler 代码但没生效 | mysql2 连接池与 instrumentation 是单例，HMR 不重载 | **必须重启 dev/prod 服务** |
| 迁移卡住不动 | 事务自死锁：事务内 `FOR UPDATE` 锁了父行，而 INSERT 的表有 FK 指向它 → INSERT 等 S 锁 = 自己等自己 | 查 `information_schema.INNODB_TRX`（同时存在 RUNNING + LOCK WAIT）；改事务内 SQL 顺序，别在事务里混用模块级 `query()` |
| 提交前想提前发现问题 | `pnpm validate:sql`（已接入 pre-commit 与 CI） | `已校验 N 条 / 可执行 M / 跳过 K / 缺陷 0` |

### 5.4 一个实例：`090_add_query_perf_indexes.sql`

2026-09 为 20 张业务表的改写后高频查询路径补了 26 条索引，是「可扩展性加固」的一部分。当前库数据量小、实测 p95 < 1ms，**这条迁移不会产生可见收益**，目标是上线后数据量放大时不退化。执行结果：声明 20 条索引全部建上、缺失 0 条；其中 2 条（`prd_standard_card.work_order_id`、`prd_material_issue_item.work_order_id`）因**列不存在**刻意跳过——那是数据模型缺口（代码已留 TODO），不是索引问题。

4. `Threads_connected` 达到 `max_connections` 的 80%。

## 7. 故障排查（本系统特有条目的）

通用排查流程、部署类、Redis 类问题见 **[12-日常运维/故障排查.md](../../12-日常运维/故障排查.md)**。以下是**该文档没覆盖、但本系统高频**的条目。

### 7.1 一页语法错误 → 全站 500（含所有 `/api/*`）

**这是本系统最危险的一类故障**：`src/app` 下任一页面文件语法错误，会让 dev server 全站 500，包括接口。

- 诊断：打开 500 页面，看错误页的 **Import traces**，能直接定位到出错文件。
- 处理：修该文件 → 重启服务。
- 预防：`pnpm validate:sql` 只能拦 SQL；语法要靠 `pnpm build` / `pnpm ts-check` 在合入前卡住。

### 7.2 页面能开但接口 403，提示「该接口尚未配置权限校验」

`src/lib/api-permissions.ts:112-119` 是 **fail-closed** 设计：路由没配权限码时**直接 403**，而不是放行。被拦的通常是新增接口忘记在 `src/lib/route-permissions-table.ts` 或 `src/lib/route-permission-extra.ts` 登记。

- `src/lib/route-permission-extra.ts:176-190` 有 9 条显式豁免（`NO_PERMISSION_ROUTES`），注释里写明：**新增时必须确认该接口确实不涉及任何业务数据读写**。
- private 路由清单见 `PUBLIC_ROUTES`（`src/lib/route-permissions-public.ts:7-18`）。

### 7.3 前端报错 401 / 302 跳登录

- 401 = token 过期（默认 24h）或被撤销（改密码、停用账号会导致 token 失效）。
- 页面路由 302 到 `/login?next=<原路径>`；API 返回 `{success:false,message:'Invalid or expired token'}`。
- 排查：`SELECT id,status,first_login FROM sys_user WHERE id=<用户ID>;` 看账号状态。

### 7.4 事件（Outbox）不消费

- 先看 §1.2 SQL-C 的 `pending` 数。
- 本项目事件表是 **`domain_event_outbox`**（另有 `sys_event_processed` 记录已处理）。
- 若 `EVENT_BUS_TYPE=db` 未配置或有 Redis 缺失告警，事件总线会降级为进程内 `memory`，**重启后事件全丢**。生产环境必须配 `EVENT_BUS_TYPE=db`。
- 发布纪律：服务层 `xxx.clearDomainEvents()` 之前**必须先把事件写进 outbox**，否则事件被静默丢弃。

### 7.5 前端报「翻译键缺失」

控制台会打 `[i18n] 翻译键缺失: xxx`。四语文案在 `messages/{zh-CN,zh-TW,en,vi}.json`。Permissions 相关额外有 `permModule.*`（26 个模块）与 `perm.*`（168 个键，四语齐平，2026-09-26 补齐）。

排查建议先跑 `pnpm validate:permissions`：它静态解析 `src/lib/permissions-catalog.ts`（`API_PERMISSIONS` / `PERMISSION_MODULES`）并与四语 `perm.*`、`permModule.*` 三方比对，能一次性定位「孤儿码 / 文案缺失 / 键多余 / 写死字符串引用」，无需连库。

### 7.6 金额/数量显示为字符串拼接（如 `8888.00100.00`）

DECIMAL 经 mysql2 返回字符串。本项目已用 `decimalNumbers: true` 根治，例外是 `ToolManagement` 的 3 个 DTO 仍返回 string。若新写接口出现这类显示，检查有没有配该选项。

### 7.7 中文日期/统计差一天

`new Date().toISOString().slice(0,10)` 取的是 **UTC 日期**，UTC+8 每天 00:00~08:00 会得到**前一天**。正解用 `src/lib/date-utils.ts` 的 `toLocalDateStr()`。

### 7.8 Git Bash 相关（Windows 开发机）

- `2>nul` 在 Git Bash 会被当成普通重定向，落盘一个叫 `nul` 的真文件；Tailwind v4 扫描到它 → Turbopack panic → 页面 500。**一律用 `2>/dev/null`**。
- `cd` 路径里的反斜杠会被吞，用正斜杠 `/d/dcprint/erp-project`。

## 附录 A：常用 SQL 速查

```sql
-- A1 某用户的全部生效权限码
SELECT DISTINCT m.permission
FROM sys_menu m
JOIN sys_role_menu rm ON m.id = rm.menu_id
JOIN sys_user_role ur ON rm.role_id = ur.role_id
WHERE ur.user_id = ? AND m.permission IS NOT NULL AND m.permission <> '';

-- A2 某用户持有的角色
SELECT r.id, r.role_code, r.role_name, r.status
FROM sys_role r JOIN sys_user_role ur ON r.id = ur.role_id
WHERE ur.user_id = ? AND r.status = 1;

-- A3 某角色关联了哪些菜单
SELECT m.id, m.menu_name, m.permission, m.parent_id
FROM sys_menu m JOIN sys_role_menu rm ON m.id = rm.menu_id
WHERE rm.role_id = ? ORDER BY m.parent_id, m.sort_order;

-- A4 用户最近登录
SELECT username, last_login_ip, last_login_time, login_fail_count, lock_time
FROM sys_user WHERE deleted = 0 ORDER BY last_login_time DESC LIMIT 20;

-- A5 解锁账号
UPDATE sys_user SET login_fail_count = 0, lock_time = NULL WHERE username = '?';

-- A6 停用账号（先备份 sys_user）
UPDATE sys_user SET status = 0 WHERE id = ? AND deleted = 0;

-- A7 最近执行的迁移
SELECT migration_name, applied_at, execution_time
FROM sys_migration ORDER BY id DESC LIMIT 20;

-- A8 事件积压
SELECT status, COUNT(*) c, MIN(create_time) oldest
FROM domain_event_outbox GROUP BY status;

-- A9 登录日志统计（近 7 天）
SELECT status, COUNT(*) c FROM sys_login_log
WHERE create_time >= DATE_SUB(NOW(), INTERVAL 7 DAY) GROUP BY status;

-- A10 缺索引审计（某表无 deleted 列索引时可作为慢查询线索）
SELECT table_name, index_name FROM information_schema.STATISTICS
WHERE table_schema = DATABASE() AND table_name = '?' AND seq_in_index = 1;
```
