## 一、执行摘要

**总体结论（一句话）**：架构骨架扎实，已达到中大型 ERP 的工程水位；但存在 **1 处高危"文档与真实库脱节"治理债** 与 **若干会悄悄破坏数据一致性的可靠性雷区**，需纳入近期主干修复。事件总线方向正确（有幂等重试 + 已搭补偿骨架），但**缺补偿编排器与业务补偿实现**，是当前最该补强的单点。

**按严重度排序的核心风险**

| 编号 | 风险 | 严重度 | 一句话影响 |
|------|------|--------|-----------|
| R1 | 文档写"无外键"，真实库 229 表/129 FK，Drizzle 零 `foreignKey()` | P0 | 误跑 `drizzle-kit push` 会 **DROP 全部 129 FK**，灾难性 |
| R2 | 事件总线 `allSettled` 并发派发，无补偿编排；`SagaCompensationHandler` 是空壳 | P0 | 下游 handler 永久失败 → 已提交 handler 不回滚 → 账实漂移 |
| R3 | split-order 审核母料扣减用 `split_order.version`(恒0) 而非母批 version | P1 | 接口 200 但库存数学静默不一致 |
| R4 | `uk_material_warehouse` 唯一索引无视软删 → `Duplicate entry` 整事务回滚 | P1 | SELECT后INSERT 写法撞唯一键，并发/软删场景丢数据 |
| R5 | `inv_inventory_log` 3 种 INSERT 形态，真实表曾仅 old 8 列 | P2 | 写路径才暴露的迁移债，曾致全模块 500 |
| R6 | 幂等标记与业务副作用是两次独立写入（双写窗口） | P2 | 标记未落库→被回收重跑→副作用重复 |
| R7 | `EventBus.publish` 只抛第一个错，无法区分瞬时/永久失败 | P2 | 永久 bug 盲重试至死信，无告警，无补偿触发 |

**路线图总览**（详见第六章）

- **Phase 0（护栏·1 周）**：禁止对 Drizzle 跑 `push/generate` + CI 护栏；修正架构文档与真实库事实对齐。
- **Phase 1（止血·2 周）**：修 R3 split-order version；全量排查 R4 同类写法；统一 R5 库存日志 INSERT 契约。
- **Phase 2（补偿·3–4 周）**：落地 R2 事件总线补偿编排 + `SagaCompensationHandler` 业务实现 + R7 错误分类。
- **Phase 3（一致性·持续）**：真实库 vs Drizzle Schema 定期差量核对自动化（逐步把 129 FK 建模回 Drizzle）；对账自愈闭环。

## 三、架构亮点（值得肯定，治理时勿破坏）

1. **DDD 分层清晰**：领域层零框架依赖、依赖方向严格自上而下；25 聚合根 / 23 应用服务 / 31 仓储实现，可测试、可演进。
2. **事件总线生产级**：Redis Streams + Outbox 两阶段 + `XAUTOCLAIM` 死消费者回收 + `IdempotentHandler` 幂等保护（`EventBus.ts` / `StreamConsumer.ts:41-53`）。
3. **安全纵深**：`access_token(JWT)` + CSRF + token 黑名单 + 限流 + 审计；proxy 只验 cookie 存在性、API 路由才验 JWT 签名，职责切分合理。
4. **并发控制成熟**：乐观锁 `version` + `transactionWithRetry` 指数退避（`src/lib/db/index.ts`）；`InventorySyncHandler.ts:34-53` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 原子 UPSERT 消除竞态。
5. **迁移机制规范**：`scripts/migrate.ts` 编号迁移 + `INFORMATION_SCHEMA` 守卫 + 幂等（`数据库架构.md` 第八节）。

## 四、风险登记表（逐条，含证据与整改方向）

### R1 ｜P0｜文档与真实库严重脱节（外键）
- **证据**：`数据库架构.md` 第六节写"不强制外键约束（应用层保证一致性）"；但工作记忆 2026-08-13 复核真实库为 **229 表 / 129 外键**；`src/lib/db/schema.ts` 经核查零 `foreignKey()`/`relations()` 定义。
- **影响**：一旦有人为"让 Drizzle 与库一致"而跑 `drizzle-kit push/generate`，会把 129 个真实 FK **全部 DROP** → 引用完整性永久丧失、级联数据孤立、历史约束失效。
- **整改方向**：
  - 立刻把"**禁止对 Drizzle 跑 `push`/`generate`**"写入 `CLAUDE.md`/开发规范硬约束；
  - CI 加护栏：扫描 `drizzle-kit` 的 push/generate 调用并 fail；
  - 建立"真实库 vs Drizzle schema"差量核对任务，把 129 FK **分批、精确**建模回 Drizzle（必须列/类型与 live 完全匹配），切忌一次性 push；
  - 修正 `数据库架构.md` 外键相关描述。

### R2 ｜P0｜事件总线缺补偿编排（已搭骨架、未实现）
- **证据**：
  - `EventBus.ts:29` `Promise.allSettled` 并发派发所有 handler；`:44-54` 仅抛**第一个**错误，不记录哪些 handler 已成功。
  - `StreamConsumer.ts:209-224`：publish 抛错则消息**不 XACK** → 走 pending + `XAUTOCLAIM` 重投 → `IdempotentHandler` 跳过已处理 handler、重试失败 handler。
  - `EventRegistry.ts:39,334-347`：`SagaCompensationHandler` 已注册监听 `saga.compensate.*` / `saga.failed` / `saga.compensated`，但注释明确"实际回滚逻辑需按业务逐步实现"。
- **影响**：当某 handler **永久失败**（如 `InventorySyncHandler` 因 schema/数据问题恒定失败 → 重试耗尽进 `dead_letter`），**已成功提交的兄弟 handler（如 `FinanceVoucherHandler` 写应付、`PurchaseInboundSyncHandler` 同步）不会被撤销** → "流水账有入库、批次缺失"类账实漂移。现有 `scripts/reconcile-inventory.cjs` 只是事后人工/定时对账，**不是自动补偿**。
- **整改方向**：见第五章（事件总线补偿设计深潜）。核心三步：① `EventBus.publish` 记录成功 handler 清单；② 新增 `SagaOrchestrator` 在永久失败时发 `saga.failed{completed:[...]}`；③ `SagaCompensationHandler` 实现各业务补偿事务（LIFO、幂等、可重试）。

### R3 ｜P1｜split-order 母料扣减 version 静默不一致
- **证据**：工作记忆 2026-08-18 记录 `warehouse/split-order` route 审核时母料扣减 `UPDATE ... WHERE id=? AND version=?` 用的是 `split_order.version`（恒 0）而非**母批自身 version**（SELECT 未取 `ib.version`），导致扣减 SQL 0 行。
- **影响**：接口返回 200，但母批库存数量未扣减 → 库存数学不一致，且**无错误日志、无告警**，最危险的"接口成功、数据错误"类别。
- **整改方向**：route 取 `ib.version AS batch_version` 并用于 WHERE；补自动化断言（审核后母批 available_qty 实际减少）。

### R4 ｜P1｜唯一索引无视软删
- **证据**：`inv_inventory.uk_material_warehouse(material_id, warehouse_id)` 不含 `deleted`（`数据库架构.md`）；已软删行仍占唯一键。原 `SELECT(deleted=0) 再 INSERT` 写法会撞 `Duplicate entry` 整事务回滚。
- **影响**：并发或遇软删行时整单回滚、进死信，业务卡死。
- **整改方向**：`InventorySyncHandler.ts:34-43` 已用 UPSERT 原子写法修复库存汇总；需**全量排查**其他路径是否仍有"先 SELECT 后 INSERT"写法，统一改为 `INSERT ... ON DUPLICATE KEY UPDATE`。

### R5 ｜P2｜库存日志 chronic 迁移缺口
- **证据**：工作记忆 2026-08-18：`inv_inventory_log` 真实表曾仅 old 8 列，代码库 3 种 INSERT 形态（old/trans/operation），补齐 13 列后才不 500。
- **影响**：只读 GET 验证发现不了，写路径才暴露的全模块 500。
- **整改方向**：统一为单一 INSERT 契约（建议以 `operation_type/operation_qty/business_type/business_no` 形态为准），废弃 old/trans 两种历史形态。

### R6 ｜P2｜幂等标记与业务副作用双写窗口
- **证据**：`IdempotencyGuard.ts:49-84`（INSERT IGNORE `processing`）与 `:93-109`（`markAsProcessed` 失败被 catch 吞掉、不抛）；handler 业务副作用在**各自事务**内先提交。
- **影响**：若业务副作用已提交、但 `markAsProcessed` 因 DB 抖动失败 → 记录残留 `processing` → 5 分钟后被 `reclaimStaleProcessing` 清理 → 事件重投 → 若 handler 本身非 SQL 级幂等则**副作用重复**。
- **整改方向**：关键 handler 保证 SQL 级幂等（如 `InventorySyncHandler` 的 UPSERT）；或将"业务副作用 + 幂等标记"放进**同一事务**（需重构 `IdempotentHandler` 的事务边界）。

### R7 ｜P2｜publish 无法区分瞬时/永久失败
- **证据**：`EventBus.ts:44-54` 仅抛第一个错误；`OutboxPoller.ts:114-134` 对 XADD 失败按 `retryCount` 盲重试至 `MAX_RETRY_COUNT` 后进死信，不区分错误类型。
- **影响**：永久 bug（代码/数据问题）与瞬时故障（网络抖动）同等对待 → 浪费重试周期、死信表堆积、无差异化告警。
- **整改方向**：引入 `isTransient(error)` 分类；瞬时错才重试，永久错直接死信并**触发 `saga.failed` 补偿** + 告警。

## 五、事件总线补偿设计深潜（R2 改造方案）

### 5.1 现状机制（已核实链路）

```
OutboxPoller.poll()                         StreamConsumer (XREADGROUP)
  claimPendingEvents()                         for each msg:
  for row:                                       eventBus.publish(event)
    StreamPublisher.publish → XADD                 └─ InMemoryEventBus.publish:
    markAsProcessed(row)                              handlers = allSettled(h1..hn)
                                                     if any rejected → throw first error
                                                 if publish ok → XACK
                                                 else → 不 XACK → pending → XAUTOCLAIM 重投
```

- `inbound.approved` 实际订阅 6 个 handler（`EventRegistry.ts:66-71`）：`InventorySyncHandler`、`FinanceVoucherHandler`、`PurchaseInboundSyncHandler`、`QrCodeGenerationHandler`、`AuditLogHandler`、`CacheInvalidationHandler`。其中前 4 为 `IdempotentHandler` 包裹的业务写。
- 失败处理依赖**幂等重试**：成功 handler 已提交事务、失败 handler 重投时被 `IdempotentHandler` 跳过。只要失败是**瞬时**的，最终一致可达成（这是当前设计的正确性基础，应予保留）。

### 5.2 根因（为何仍会漂移）

1. `EventBus.publish` 用 `allSettled` 但**不收集"已成功 handler 清单"**，失败时无从知道该补偿谁。
2. **没有编排器**在 handler 永久失败（死信）时发出补偿指令——`SagaCompensationHandler` 通道已注册却**无人触发、逻辑为空**。
3. 补偿事务本身未实现：即便收到 `saga.compensate.*`，也无具体"撤销已提交应付/已同步入库"的业务 SQL。

### 5.3 改造目标

- 保留"幂等重试"作第一道防线（应对瞬时故障）。
- 增加"补偿编排"作第二道防线（应对永久故障）：**永久失败时自动撤销已提交兄弟 handler 的副作用**，恢复业务一致。
- 错误分类，避免永久 bug 盲重试。

### 5.4 改造方案（代码级落地）

**步骤 1 — `EventBus.publish` 记录成功 handler 清单**
`src/infrastructure/event-bus/EventBus.ts`：在 `allSettled` 后，除抛出第一个错误外，附带 `completedHandlers`（已成功执行的 handler 名列表）到错误对象或单独回调。

```ts
// 伪代码示意
const results = await Promise.allSettled(handlers.map(h => h.handle(event)));
const completed: string[] = [];
const failures: {name: string; reason: unknown}[] = [];
results.forEach((r, i) => {
  const name = handlerNames[i];
  if (r.status === 'fulfilled') completed.push(name);
  else failures.push({ name, reason: r.reason });
});
if (failures.length) {
  const err = failures[0].reason instanceof Error ? failures[0].reason
            : new Error(String(failures[0].reason));
  (err as any).completedHandlers = completed;   // 供编排器构造补偿清单
  throw err;
}
```

**步骤 2 — 新增 `SagaOrchestrator`（检测永久失败 → 发 `saga.failed`）**
`src/application/saga/SagaOrchestrator.ts`：在 `OutboxPoller` 标记 `dead_letter` 处（`OutboxPoller.ts:114-116`、`171-177`）挂钩；读取错误的 `completedHandlers`，发布领域事件 `saga.failed`：

```ts
// OutboxPoller 标记死信时
if (retryCount >= MAX_RETRY_COUNT) {
  await outbox.markAsDeadLetter(row.id, errorStack);
  const completed = (publishError as any)?.completedHandlers ?? [];
  if (completed.length) sagaOrchestrator.fail(row.eventType, row.id, completed); // → 发 saga.failed
}
```

**步骤 3 — 实现 `SagaCompensationHandler` 业务补偿（LIFO、幂等、可重试）**
`src/application/handlers/SagaCompensationHandler.ts`（当前为空壳）：按 `saga.compensate.*` 主题实现各业务补偿事务，例如：
- `saga.compensate.finance_cost` → 冲销已生成的应付/凭证；
- `saga.compensate.inventory_inbound` → 扣回已同步的入库批次与汇总（与 `InventorySyncHandler` 逆操作，复用同一事务 + UPSERT 语义）；
- 补偿本身用 `INSERT ... ON DUPLICATE KEY UPDATE` / 状态机，保证**幂等**；失败重试直至成功或进补偿死信（需告警）。

**步骤 4 — 错误分类 `isTransient(error)`**
`src/infrastructure/event-bus/errors.ts`：瞬时（连接超时/锁等待/网络）才重试；永久（约束冲突/数据非法/代码 bug）直接死信并触发补偿，避免盲重试浪费周期。

### 5.5 涉及文件清单

| 文件 | 改动 |
|------|------|
| `src/infrastructure/event-bus/EventBus.ts` | 收集 `completedHandlers` |
| `src/infrastructure/event-bus/errors.ts`（或新建） | `isTransient()` 错误分类 |
| `src/infrastructure/event-bus/OutboxPoller.ts` | 死信处挂钩 `sagaOrchestrator.fail` |
| `src/application/saga/SagaOrchestrator.ts`（新建） | 发 `saga.failed` |
| `src/application/handlers/SagaCompensationHandler.ts` | 实现各业务补偿事务 |
| `src/application/EventRegistry.ts` | 注册补偿主题（已有，补充实现） |

### 5.6 验收标准

- [ ] 注入一个"永久失败 handler"的集成测试：断言其兄弟 handler 的副作用被 `saga.compensate.*` **自动撤销**，对账为 0。
- [ ] `domain_event_outbox` 死信行可追溯到对应的 `saga.failed` 与补偿执行记录。
- [ ] 瞬时故障仍走幂等重试（不触发补偿）；永久故障不盲重试、直接补偿 + 告警。
- [ ] 补偿 handler 自身失败可重试、幂等，不重复冲销。
