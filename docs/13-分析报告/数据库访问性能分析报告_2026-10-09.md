## 二、P0 问题 — 索引失效（函数套列）

### 2.1 时间函数套列（全表扫描）

**规则**：`WHERE YEAR(col) = ?` 或 `WHERE col >= ? AND col < ?` 是两种完全不同的执行计划：前者全表扫描，后者命中 `(deleted, create_time)` 复合索引。

**影响面**：~49 处，集中在以下模块：

| 模块 | 典型写法 | 命中文件 |
|------|----------|---------|
| 质量模块 stats | `WHERE deleted=0 AND YEAR(create_time)=YEAR(CURDATE()) AND MONTH(create_time)=MONTH(CURDATE())` | `quality/*/stats/route.ts` × 8 个文件 |
| 设备模块 stats | `WHERE YEAR(inspection_date)=YEAR(CURDATE()) AND MONTH(inspection_date)=MONTH(inspection_date)` | `equipment/*/stats/route.ts` × 5 个文件 |
| 采购订单 stats | `WHERE deleted=0 AND YEAR(create_time)=YEAR(CURDATE()) AND MONTH(create_time)=MONTH(CURDATE())` | `purchase/*/stats/route.ts` |
| 生产排产 stats | `WHERE YEAR(schedule_date)=YEAR(CURDATE()) AND MONTH(schedule_date)=MONTH(CURDATE())` | `hr/schedules/stats/route.ts` |
| 仪表板 CEO | `WHERE deleted=0 AND DATE(create_time)=CURDATE()` | `dashboard/ceo/route.ts` × 3 处 |
| 仪表板生产 | `WHERE deleted=0 AND DATE(create_time)=CURDATE()` | `dashboard/production/route.ts` |
| 仪表板销售 | `GROUP BY DATE_FORMAT(order_date, '%Y-%m')` | `dashboard/sales/route.ts` |
| 财务账龄 | `DATEDIFF(CURDATE(), create_time) <= N` | `finance/aging/route.ts` |
| 耗材库存 | `DATEDIFF(expire_date, CURDATE()) <= 7` | `dcprint/ink-surplus/route.ts` |
| SGS 到期预警 | `DATEDIFF(expire_date, CURDATE()) <= ?` | `quality/sgs/expiry-warning/route.ts` |

**修复方向**：将函数套列替换为半开区间，例如：

```sql
-- ❌ 失效索引
WHERE deleted = 0 AND YEAR(create_time) = YEAR(CURDATE()) AND MONTH(create_time) = MONTH(CURDATE())

-- ✅ 命中 idx_deleted_create_time
WHERE deleted = 0 AND create_time >= DATE_FORMAT(CURDATE(), '%Y-%m-01')
  AND create_time < DATE_FORMAT(DATE_ADD(CURDATE(), INTERVAL 1 MONTH), '%Y-%m-01')
```

**已有对应迁移**：`database/migrations/090_add_query_perf_indexes.sql` 已为 `inv_material`、`inv_inventory`、`inv_inbound_order`、`inv_outbound_order`、`prd_work_order`、`inv_stocktaking`、`qrcode_record`、`biz_order_header/line`、`sal_order`、`pur_purchase_order` 等加建了 `(deleted, create_time)` 组合索引。**但 SQL 代码未同步改写**，导致索引建了却用不上。

### 2.2 CAST 隐式类型转换（索引失效）

**规则**：`CAST(pc.product_code AS UNSIGNED) = sc.id` 中，若 `product_code` 是 VARCHAR 列，MySQL 会对每行做类型转换，无法走索引。

**影响面**：54 处，核心是质量模块两个路由：

| 文件 | 行号 | 问题 |
|------|------|------|
| `quality/process/route.ts` | 120 | `CAST(pc.product_code AS UNSIGNED) = sc.id` |
| `quality/final/route.ts` | 83 | 同左 |
| `migrations/readmd-fixes/route.ts` | 369 | `CAST(a.employee_id AS UNSIGNED) = e.id` |
| `migrations/six-critical-fixes/route.ts` | 341 | `CAST(se.id AS CHAR)` + COLLATE 比较 |

**修复方向**：在 `prd_standard_card.id` 旁维护一个VARCHAR 兼容列，或在 `prd_process_card` 表中将 `product_code` 改为 INT（当前迁移 `20260930_fix_process_card_product_ref.sql` 已将 product_code 回填为标准卡 ID 字符串，但 JOIN 条件仍未类型对齐）。

## 三、P1 问题 — 串行多 COUNT 查询

### 3.1 Dashboard 类接口多 COUNT 串行调用

**典型模式**（以 `dashboard/ceo/route.ts` 为例）：

```sql
-- 每次调用都是独立查询，串行执行，累积延迟
SELECT COUNT(*) FROM prd_process_card WHERE deleted=0 AND DATE(create_time)=CURDATE()  -- ①
SELECT COUNT(*) FROM sal_order WHERE deleted=0 AND DATE(create_time)=CURDATE()        -- ②
SELECT COUNT(*) FROM inv_outbound_order WHERE deleted=0 AND DATE(create_time)=CURDATE() -- ③
SELECT COUNT(*) FROM qc_inspection WHERE deleted=0                                     -- ④
SELECT COUNT(*) FROM inv_warehouse WHERE deleted=0                                     -- ⑤
```

**影响**：单接口 N 次往返，N 越大 RTT 累积越明显。

**修复方向**：合并为单条 SQL，用多个标量子查询：

```sql
SELECT
  (SELECT COUNT(*) FROM prd_process_card WHERE deleted=0 AND create_time >= CURDATE()) AS process_today,
  (SELECT COUNT(*) FROM sal_order     WHERE deleted=0 AND create_time >= CURDATE()) AS order_today,
  (SELECT COUNT(*) FROM inv_outbound_order WHERE deleted=0 AND create_time >= CURDATE()) AS outbound_today,
  (SELECT COUNT(*) FROM qc_inspection WHERE deleted=0) AS inspection_total,
  (SELECT COUNT(*) FROM inv_warehouse WHERE deleted=0) AS warehouse_count
```

### 3.2 Stats 模块同类问题

`quality/process/stats/route.ts` 中 5 次独立 COUNT：

```sql
SELECT COUNT(*) FROM prd_process_card WHERE deleted=0 AND burdening_status IN (1,2)
SELECT COUNT(*) FROM prd_process_card WHERE deleted=0 AND burdening_status=2
SELECT COUNT(*) FROM prd_process_card WHERE deleted=0 AND burdening_status=3
SELECT COUNT(*) FROM inv_trace_record WHERE DATE(create_time)=CURDATE()
SELECT COUNT(*) FROM inv_trace_record WHERE create_time >= DATE_SUB(CURDATE(),INTERVAL 7 DAY)
```

**修复方向**：合并为单次扫描：

```sql
SELECT
  SUM(burdening_status IN (1,2)) AS pending,
  SUM(burdening_status = 2)      AS inspecting,
  SUM(burdening_status = 3)      AS passed
FROM prd_process_card WHERE deleted=0

SELECT
  SUM(DATE(create_time) = CURDATE())    AS today,
  SUM(create_time >= DATE_SUB(CURDATE(), INTERVAL 7 DAY)) AS week
FROM inv_trace_record WHERE deleted=0
```

## 五、P2 问题 — OFFSET 深翻页退化

### 5.1 现状

`LIMIT ? OFFSET ?` 共 117 处，全部使用传统分页。当 offset 较大时（如第 100 页，每页 20 条），MySQL 需扫描并丢弃前 1980 行。

### 5.2 影响

| 场景 | 风险等级 |
|------|---------|
| 管理后台（用户通常看前 3 页） | 🟢 低 |
| 追溯/日志类页面（可能翻到 50+ 页） | 🟡 中 |
| 批量导出（无分页直接全量查询） | 🔴 高 |

### 5.3 高关注路由

| 路由 | 说明 |
|------|------|
| `/api/trace/label` | 追溯查询，无 WHERE 条件限制时全表扫描 |
| `/api/qrcode/unified-trace` | 二维码追溯，多表关联查询 |
| `/api/warehouse/batch-inventory` | 库存批次查询，数据量随时间增长 |
| `/api/dcprint/trace` | 全流程追溯，JOIN 较多 |

## 八、JOIN 性能分析

### 8.1 高频 JOIN 模式

| JOIN 模式 | 出现次数 | 风险 |
|-----------|---------|------|
| `LEFT JOIN crm_customer c ON so.customer_id = c.id` | ~8 处 | 中等（customer 表小，约 100 行） |
| `LEFT JOIN inv_material m ON ib.material_id = m.id` | ~6 处 | 中等（material 表约 500 行） |
| `LEFT JOIN inv_warehouse w ON ...warehouse_id = w.id` | ~10 处 | 低（warehouse 表约 10 行） |
| `LEFT JOIN inv_location l ON ...location_id = l.id` | ~6 处 | 低 |
| `LEFT JOIN prd_standard_card sc ON CAST(pc.product_code AS UNSIGNED) = sc.id` | 2 处 | 🔴 高（CAST 使索引失效，见 2.2） |
| `LEFT JOIN sys_employee e ON ...create_by = e.id` | ~5 处 | 低 |

### 8.2 高风险 JOIN 修复

**`quality/process/route.ts` 第 117-121 行**（已在之前讨论中修复，此处记录）：

```sql
-- 修复前（索引失效）
LEFT JOIN prd_standard_card sc ON CAST(pc.product_code AS UNSIGNED) = sc.id

-- 修复后（类型对齐）
LEFT JOIN prd_standard_card sc
  ON pc.product_code IS NOT NULL AND pc.product_code != ''
  AND CAST(pc.product_code AS UNSIGNED) = sc.id
```

## 九、分页策略评估

### 9.1 当前分页实现

```typescript
// src/lib/db/index.ts:522
const paginatedSql = `${sql} LIMIT ? OFFSET ?`;
```

所有 117 处分页均使用 `LIMIT offset, size` 传统分页。

### 9.2 退化阈值估算

假设最坏情况（无 WHERE 条件 + 大 offset）：

| 表 | 预估行数 | offset=2000 | offset=10000 | 建议最大页码 |
|----|---------|-------------|-------------|------------|
| `inv_trace_record` | ~100k（生产后） | ~50ms | ~250ms | 50 |
| `prd_work_order` | ~50k | ~25ms | ~120ms | 50 |
| `qrcode_record` | ~200k | ~100ms | ~500ms | 30 |
| `sys_operation_log` | ~500k | ~250ms | ~1s+ | 20 |

### 9.3 建议优化方向

将高频追溯类列表页改为**游标分页**（`WHERE id < ? ORDER BY id DESC LIMIT ?`），避免深翻页性能退化。
