# BUG 修复报告：admin 登录后「没有权限」

- 日期：2026-09-15
- 报告对象：用户报告「用户:admin 密码:admin123 没有权限」
- 结论：**已定位并修复**（迁移 `082`）；同时发现一个**同源但未修**的严重缺陷（见 §5）

---

## 1. 症状与第一轮定性

| 探测 | 结果 |
|---|---|
| `POST /api/auth/login {admin, admin123}` | **HTTP 200**，下发 token/refresh_token/csrf_token |
| 12 个代表性受保护接口（dashboard/customers/materials/workorders/orders/system/roles/settings/finance/hr） | **全部 HTTP 200** |
| 登录响应 `data.user.permissions` | **`[]`（空数组）** |
| `GET /api/auth/menus` | **`menus: []`（0 条）、`permissions: 0`** |

⇒ **服务端并没有 403**。「没有权限」不是 API 层拒绝，而是**登录态里没有任何菜单与权限**，
界面因此无任何可访问功能（在 storage/cookie 错配时还会叠加 BUG-006 的永久转圈，
因为 `AuthContext.tsx:141` 用 `initialAuth.menus.length > 0` 判定 `ssrAuthenticated`，空菜单 ⇒ `authResolved` 恒 false）。

## 2. 根因（数据层，已实证）

权限与菜单走的是同一张关联表 `sys_role_menu`：

- `src/lib/auth.ts:231-237`（`getUserInfo` 产 permissions）
- `src/app/api/auth/menus/route.ts:66-76`
- `src/app/api/auth/login/route.ts:305-314`
- `src/lib/menu-service.ts:78`

三者都是 `sys_menu ⋈ sys_role_menu ⋈ sys_user_role`。

**迁移前实测 `sys_role_menu` 按角色分布：**

| role_id | role_code | 绑定菜单数 |
|---|---|---|
| **1** | **super_admin** | **0** ← 缺陷 |
| 2 | business_manager | 19 |
| 3 | sales | 11 |
| 4 | engineer | 20 |
| 5 | production_manager | 27 |
| 6 | warehouse_manager | 18 |
| 7 | warehouse_keeper | 12 |
| 8 | purchaser | 17 |
| 9 | qc_inspector | 19 |
| 10 | accountant | 12 |
| 21/22 | VERIFY_*（QA 临时角色） | 1 / 1 |

`sys_menu` 有 111 行（`status=1, deleted=0`）。**超级管理员是唯一一个一条绑定都没有的角色。**

**种子层根因**：`src/app/api/init/settings-seed/route.ts:1390-1419` 的 `roleMenuAssignments`
映射表只列了 9 个业务角色，**遗漏 `super_admin`**，且该处用的是 `INSERT IGNORE`，
所以既不报错也不补绑。

而设计意图其实写得很明确 —— `src/app/api/init/menus/route.ts:1469-1490`：

```ts
const [roles] = await conn.execute("SELECT id FROM sys_role WHERE role_code = 'super_admin' LIMIT 1");
// 然后 SELECT id FROM sys_menu WHERE status = 1，逐条 INSERT INTO sys_role_menu
```

即「super_admin 绑定全部菜单」。这条修复路径显然从未在菜单扩充后被执行过。

> 附注：仓库里已有 `scripts/fix-admin-role.ts` 与 `scripts/fix-admin-menus.js` 两个历史修复脚本，
> 说明这是**复发过的问题**，不是一次性事故。

## 3. 修复

新增正式迁移 `database/migrations/082_grant_super_admin_all_menus.sql`（幂等）：

```sql
INSERT IGNORE INTO sys_role_menu (role_id, menu_id)
SELECT r.id, m.id
FROM sys_role r
CROSS JOIN sys_menu m
WHERE r.role_code = 'super_admin'
  AND r.deleted = 0
  AND m.deleted = 0
  AND m.status = 1;
```

依据库里已存在的唯一键 `uk_role_menu(role_id, menu_id)` 保证可重复执行。
未使用 `migrate up`（pending 队列含 `057_unify_pk_to_bigint` 等高危项），
改用受控执行器 `.workbuddy/tmp/mig-082.mjs` 只跑这一个文件。

**执行结果**

|---|---|---|
| `sys_role_menu` 总行数 | 157 | **268** |
| super_admin 绑定行数 | **0** | **111** |
| admin 可见权限点（经 join 实算） | **0** | **111** |
| 受影响行数 | — | `affectedRows=111` |

已登记 `sys_migration`（batch 68）。

## 5. 同源缺陷：权限码词汇表三套、交集为 0 —— **已按方向 3 修复**

修完 §3 之后，「admin 没有权限」已解决，但顺带查出一个会让**所有非超管账号必然 403** 的既有缺陷。

系统里存在**三套互不相通的权限码词汇表**：

| 来源 | 数量 | 形态 | 谁在读 |
|---|---|---|---|
| `API_PERMISSIONS`（`src/lib/permissions-catalog.ts`） | **163** | `order:view`、`warehouse:create`（单数模块+动作） | **网关 `withPermission` 实际校验的就是这套** |
| `sys_menu.permission`（111 行菜单） | **111** | `orders:*`、`warehouse:*`、`settings:*`（**全部带 `*`**，复数模块） | `getUserInfo` / 登录 / menus 产出给用户 |
| `sys_role.permissions`（json 列） | 161/2/1… | 超管是**API 码**（`order:view`），其余角色是**菜单码**（`orders:*`） | 角色权限 UI 保存，`getUserInfo` **完全不读** |

审计脚本 `.workbuddy/tmp/perm-vocab-audit.mjs` 实测：

```
API_PERMISSIONS 权限码总数 = 163
sys_menu.permission 总数 = 111   （带 * 的 111，不带 * 的 0）
两边交集 = 0 个
网关要校验但 sys_menu 无同名值 = 163 / 163
```

而 `src/lib/auth.ts:252-258` 的判定是**字面量比较、不做通配符展开**：

```ts
export function hasPermission(userInfo, permission) {
  return userInfo.permissions.includes(permission)   // 'orders:*' ≠ 'order:view'
      || userInfo.permissions.includes('*')          // 没有任何角色是 ['*']
      || userInfo.roles.includes('admin')
      || userInfo.roles.includes('super_admin');     // ← admin 全靠这一条
}
```

**用真实的 `hasPermission` 函数实测（`.workbuddy/tmp/perm-vocab-proof.mts`，`import` 的是 `src/lib/auth.ts` 本体，非重新实现）：**

| 账号（库中真实角色/权限） | `order:view` | `warehouse:view` | `finance:view` | `system:config` |
|---|---|---|---|---|
| super_admin（admin） | 放行 | 放行 | 放行 | 放行 |
| business_manager（zhangwei，`["orders:*","crm:*"]`） | **403** | **403** | **403** | **403** |
| warehouse_manager（zhaolei，`["warehouse:*"]`） | **403** | **403** | **403** | **403** |
| accountant（wufang，`["finance:*"]`） | **403** | **403** | **403** | **403** |

反证：把 `permissions` 换成 API 词汇表的精确码，`hasPermission('order:view') === true`。

**影响**：除 super_admin 外的 9 个角色，**一旦走过首次登录改密（`first_login` 0），每个受权限保护的接口都会 403**。
目前这些账号 `first_login=1` 且从未登录，这个坑还没被踩到 —— 所以它是一枚**未引爆的地雷**，
而不是当前正在发生的故障。admin 之所以一直「能用」，纯属 `roles.includes('super_admin')` 这条硬绕过。

**修复方向（三选一，需产品/你定）**

1. **统一到 API 词汇表**：把 `sys_menu.permission` 的 111 条改写为 `API_PERMISSIONS` 的精确码
   （一个菜单可能对应多个 API 码 → 需拆成权限点菜单或加映射表）；同时把 `sys_role.permissions` 里
   9 个角色的 `orders:*` 式也改成精确码。**最正，工作量最大，需逐菜单确认语义。**
2. **让 `getUserInfo` 改读 `sys_role.permissions`**（超管那份已经是 161 个 API 码），
   并把其余 9 个角色的通配符改写成 API 码。改动小，但 `sys_role.permissions` 与菜单可见性脱钩。
3. **给 `hasPermission` 加别名+通配符匹配**（`orders:*` → `order:*`）。
   最省事但是**治标**：复数/单数、`settings` vs `system` 等差异仍需一张别名表，长期是又一层技术债。

**→ 2026-09-15 定案：选方向 3（通配符 + 别名），已实施并通过验证。** 长期仍建议立项做方向 1。

### 5.1 修复实施（方向 3）

**新增 `src/lib/permission-match.ts`**（零依赖，服务端/客户端均可 import）：

- `PERMISSION_MODULE_ALIASES`：模块别名表（菜单词汇段 → API 词汇段），共 10 条：
  `orders→[order,workorder,delivery,bom,customer,product]`（订单域）、
  `dashboard_center→dashboard`、`engineering→[standard-card,sample]`、
  `customers→customer`、`products→product`、`sales→order`、
  `manage→qrcode`、`die-template→prepress`、`labels→dcprint`、`process-cards→dcprint`
- `READ_ONLY_ACTIONS`：`view/list/query/stats/schedule/search`
- `matchPermission(held, required)` 匹配规则（v3，经两轮越权推演收紧）：
  1. 精确码 / 全局 `*` 直接命中；
  2. **2 段顶层通配** `a:*`（目录=整个域）：`a` 别名展开命中请求首段即放行，不限动作；
  3. **3+ 段子菜单通配** `a:b:*`：仅**尾段** `b` 别名展开命中请求「首段或动作位」才放行
     ——不做中间段/首段命中（v1 曾因段级任意命中导致
     `settings:warehouse-category:*` 放行整个 `warehouse`，已废弃）；
  4. **dashboard 展示型特判**：`dashboard:*` 持有码命中后仅放行只读动作位
     （v2 曾让 `dashboard:warehouse:*` 放行仓库写权限，已收紧）。
- `hasPermissionIn(permissions, required)`：集合判定入口。

**`src/lib/auth.ts` `hasPermission` 改造**：super_admin/admin 角色硬绕过保持前置不变；
字面量 `includes` 保持；新增 `hasPermissionIn` 通配展开兜底。

**别名表维护规则**：新增菜单模块时，若其权限码模块名与 `API_PERMISSIONS` 不一致，必须登记别名。

### 5.3 已知放宽点与残留缺口（方向 3 的代价，方向 1 时一并消除）

| 类型 | 条目 | 说明 |
|---|---|---|
| 放宽 | `orders` 尾段展开为整个订单域 | `sample:orders:*`、`purchase:orders:*` 也会拿到 order/workorder/customer/product/delivery/bom 全套（域内语义成立，略宽） |
