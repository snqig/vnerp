## 1. 根因（已实测确认）

`src/lib/db/index.ts:42-57` 的 `dbConfig` **既无 `decimalNumbers: true` 也无 `typeCast`**，
因此 mysql2 把 MySQL `DECIMAL` / `NEWDECIMAL` 列**一律以字符串返回**（全库 280 个 distinct DECIMAL 列名）。

运行时实测（登录后直接取接口字段类型）：

| 接口 | 字段 | 实际类型 |
|---|---|---|
| `/api/dcprint/tool` | `unit_cost` / `net_value` | `string("0.5")` / `string("500")` |
| `/api/dcprint/ink-formula` | `theoretical_cost` | `string("0.0000")` |
| `/api/purchase/return` | `total_amount` | `string("0.00")` |
| `/api/production/orders` | `plan_qty` | `number(0)`（该接口服务端已算好） |
| `/api/hr/salary` | `basic_salary` | `string("8888.00")`（前一轮已证） |

**衍生两类故障**：

1. `字符串 + 值` → **字符串拼接**（合计变 `"8888.00100.00"`）
2. `字符串 - 值` / `字符串.toFixed()` / `字符串.toLocaleString(带参)` → **`NaN` 或 TypeError（页面白屏）**

> 注意 `*` / `/` 会强制转数值，故 `item.quantity * item.unit_price` **不受影响**——扫描器已据此排除。

## 2. 扫描方法（三级收敛，避免误报）

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 正则提取 `.toFixed(` / `.toLocaleString()` / `.reduce(` 且未被 `Number()\|parseFloat()\|parseInt()` 包裹 | 239 / 125 / 213 调用；未归一命中 236 + 160 |
| 2 | 用「属性名 ∈ DB DECIMAL 列名（280 个）」过滤，区分 **DB 来源** vs **客户端计算量** | 收敛到 69 + 3 |
| 3 | 只取表达式**最后一个属性名**；含 `*`、`/` 视为已强制转数值 | 收敛到 **58**（T1 页面 31 / T2 API 5 / T3 域·应用·库 22） |

> 关键洞察：API 透传的是 **snake_case 列名**，客户端计算量多为 **camelCase**，
> 用列名集合过滤可天然把「危险」与「安全」分开。

## 6. 根因解法 —— 方案 A 已执行 ✅

### 6.1 改动（db 层一处把握根因）

`src/lib/db/index.ts` 的 `dbConfig` 新增：

```ts
// ── DECIMAL 读取类型（在 DB 边界统一收敛，而不是逐个调用点打补丁）──
// 默认 mysql2 把 DECIMAL/NEWDECIMAL 读成字符串（如 basic_salary → "8888.00"），
// 引发字符串拼接（¥NaN / 长串）与 `.toFixed()` TypeError（页面白屏）。
// 与同文件 normalizeIsoDatetime 对 ISO 时间戳的处理同一思路：边界收敛。
decimalNumbers: true,
```

**⚠️ 生效前提：必须重启 dev server。** 连接池是 `globalThis` 单例（`if (!globalForDb.pool)`），
HMR/热重载**不会重建**已缓存的 pool —— 只改文件不重启，运行时行为不变。
（本次已按 PID 精准 kill 后重启 `next dev -p 5000`，并以此验证。）

### 6.4 唯一例外：`/api/dcprint/tool`（20 处，**刻意保留**）

根因**不在 db 层**，而是**应用层显式转换**：

`src/application/services/ToolManagementService.ts:29-32, 105-108`

```ts
export interface ToolListItem {
  original_cost: string;      // ← 契约声明本身就是 string
  accumulated_cost: string;
  net_value: string;
  unit_cost: string;
}
// ...
original_cost: String(tool.originalCost),   // ← 显式转回字符串
accumulated_cost: String(tool.accumulatedCost),
net_value: String(tool.netValue),
unit_cost: String(tool.unitCost),
```

即 `decimalNumbers` **已生效**（仓储拿到的是 number），但 DTO 层又 `String()` 转回。

**判定：保留不改。** 理由：

- 显式 `String()` 是**模块级刻意契约**（同类还有 `ToolUsageRecord.amortized_cost: string`、`ToolMaintenanceRecord.maintenance_cost: string`），
  它不是**隐式**缺陷源 —— 而本报告针对的是隐式字符串引发的 `NaN` / TypeError
- 它**不产生** `NaN`、**不产生** TypeError；消费端 `dcprint/tool` 与 `dcprint/tool-manage` 均已 `Number(x).toFixed()` 兜底，对 string / number 入参都成立
- 改成 number 需重构 3 个公开 DTO 接口 + 2 个页面类型声明，收益仅「契约一致性」，风险是未知消费端

**遗留的一致性瑕疵（建议后续统一，二选一）**：同一字段两页声明矛盾 ——

| 页面 | 声明 | 与当前 API 是否一致 |
|---|---|---|
| `dcprint/tool/page.tsx:60-63` | `unit_cost: string` | ✅ 一致（但内部又 `Number()` 包裹，声明形同虚设） |
| `dcprint/tool-manage/page.tsx:62-64` | `unit_cost: number` | ❌ 不一致（因 `Number()` 兜底故未暴露） |

> 结案口径：**方案 A 已完成**，隐式字符串类缺陷在全仓 14 个代表接口 / 15 个页面上**归零**；
> 余下唯一例外是 1 个模块的**显式** DTO 契约，非缺陷。
