## 5 · 过程中发现的两个新隐患（已处置 / 待处置）

### 5.1 已处置：`pnpm migrate up` 会推翻 087

`scripts/migrate.ts` 用**完整文件名（含扩展名）**登记 `sys_migration`，而我最初给 085/086/087
登记时剥掉了扩展名 → 运行器会视为"未执行"而重跑（085/086 有幂等守卫，安全；087 的守卫
`is_splittable=1` 也会使重跑无效果，但登记口径仍须修正）。

更严重的是：`20260827132300_add_is_splittable.ts` **效果已在库中却从未登记**，
若执行 `pnpm migrate up`，它的 `UPDATE ... SET is_splittable = 1 WHERE category_code IN (FILM,PAPER,PKG,RAW)`
会**把 784 行全部重新置 1，直接推翻 087**。已先核实列与索引均存在，再登记为已应用（batch 73）。

> 附带发现：仓库尚有 **30 个待执行迁移**（021/022/057–078/083 等），
> 说明 `pnpm migrate` 这条链路长期未被使用，DDL 多由 `/api/migrations/*` 与
> `/api/init/*` 路由执行。这解释了为何"迁移文件存在"与"效果已存在"会脱节。

### 5.2 待处置：`MaterialCostProvider` 降级分支的 id 域不匹配

```ts
// src/infrastructure/providers/MaterialCostProvider.ts:41
`SELECT id, unit_price FROM base_ink WHERE id IN (${missingIds})`
```

`missingIds` 来自 `inv_material.id`，却拿去匹配 `base_ink.id` —— 两表 id 域不同，
这是一个**恒不命中或错配**的查询。属独立缺陷，未纳入本批改动，需你决定：
是删除该降级分支（既然 `weighted_avg_cost` 已可用），还是改为按 `material_code` 关联。
