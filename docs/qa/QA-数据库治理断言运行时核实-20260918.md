# QA · 运行时核实报告 —「数据库治理 5/10」断言

- **核实时间**：2026-09-18
- **对象**：外部评估报告中「数据库治理 5/10 · Schema 覆盖不完整，SQL/迁移/ORM 多来源并存」
- **方法**：只读探针（information_schema + 静态扫描）+ 匿名 HTTP 探测，全部以运行时实测为准，不采信文档自述

## 一、结论

**报告的判定方向属实，但数字失准、范围显著低估。**

| 断言 | 核实结果 | 实测值 |
|---|---|---|
| Schema 覆盖不完整 | ✅ 属实 | 覆盖率 **80.7%**（243/301 业务表），58 张未建模 |
| SQL / 迁移 / ORM 多来源并存 | ✅ 属实，**且比报告描述的更严重** | 实测 **6 个**定义来源，非报告暗示的 3 个 |
| 隐含基数「327 张表」 | ❌ 失准 | 实际 **366** 基表 / 301 业务表 / 372 关系 |
| 隐含「120 条 FOREIGN KEY」 | ⚠️ 来源错误 | 该数字取自**滞后快照文件**；实际库 **163** 条 |
| Drizzle 无外键/关系定义 | ❌ 已过时 | 实测 **131 处 `foreignKey()`**、0 处 `relations()` |

**报告完全未发现的两个来源**，恰是风险最高的：
1. **SQL 语句被存放在 i18n 消息文件里**，由 30 个 API 路由用翻译函数取出执行（246 个 DDL 键）
2. **20 个 API 端点可运行时建表**（16 个 `/api/init` + 4 个 `/api/migrations`）

## 五、新增发现（报告未提及）

### 5.1 SQL 语句存放在 i18n 消息文件并被直接执行 ⚠️

`src/app/api/init/inbound-tables/route.ts` 中，建表 SQL 常量 `_CREATE_TABLES_SQL` 是**死代码**，真正执行的是：

```ts
await query(ts('k_1yw7bpa'));   // 值 = "CREATE TABLE IF NOT EXISTS inv_inbound_order (...)"
```

实测消息文件内容：

| i18n key | 实际值（截断） | 长度 |
|---|---|---|
| `k_1yw7bpa` | `CREATE TABLE IF NOT EXISTS inv_inbound_order (` | 1446 |
| `k_1kkze5m` | `CREATE TABLE IF NOT EXISTS inv_inbound_item (` | 1186 |
| `k_rdgv2l` | `CREATE TABLE IF NOT EXISTS inv_inventory_batch (` | 1555 |
| `k_1ecjvlf` | `INSERT INTO inv_inbound_order (...) VALUES` | 587 |

四语言文件**各含 193 个 `CREATE TABLE` + 31 个 `INSERT INTO`**。

**成因**：i18n codemod 把含中文注释的 SQL 当作「硬编码中文」抽取为合成键。

**风险**：
- SQL 由翻译文件驱动 → 任何能改 `messages/*.json` 的路径都能改变实际执行的 SQL
- 多语言理论上可执行不同 SQL（本次核实四语言内容一致，尚未分歧）
- `ts()` 是异步翻译查表，把一个纯本地化机制变成了 DDL 执行通道

### 5.2 API 端点运行时建表

| 路由 | SQL 调用点 | 鉴权 |
|---|---|---|
| `/api/init/full-tables` | **66** | withPermission |
| `/api/migrations/readmd-fixes` | 11 | withPermission |
| `/api/init/three-layer-tables` | 10 | withPermission |
| `/api/init/po-grn-tables` | 9 | withPermission |
| `/api/migrations/six-critical-fixes` | 7 | withPermission |
| `/api/init/inbound-tables` | 6 | withPermission |
| 其余 24 个路由 | 各 1–6 | withPermission |

**GET 触发写操作**：`/api/migrations/readmd-fixes` 的 `GET` 处理器无条件执行 `ALTER TABLE`（仅 `tableExists`/`columnExists` 幂等保护），违反 HTTP 安全语义 —— 浏览器预取、爬虫、扫描器均可能触发。

### 5.3 纵深防御只剩一层

`src/proxy.ts`：

```ts
const BLOCKED_ROUTES = ['/qrcode', '/api/init', '/api/debug', '/api/diagnose'];  // 仅 NODE_ENV=production 生效
// 公开 API 白名单（无需 token）：
'/api/migrations',
```

- `/api/init` 仅在 **production** 被 404 拦截；**dev 环境完全不拦**
- `/api/migrations` **不在** `BLOCKED_ROUTES`，却被列入**公开白名单** → 生产环境 proxy 层放行
- 实际拦截全靠路由内的 `withPermission` 一层

### 5.4 顺带发现

`GET /api/health` 返回 **503 degraded**（本次未深查，建议单独排期）。

## 七、对 5/10 评分的判断

评分的**方向正确**（覆盖不完整、来源并存均属实），但：

- **低估了严重性**：漏掉 i18n SQL 与运行时 DDL 两个高风险来源
- **基数不准**：327 表 / 120 FK 均来自滞后或错误的来源
- **遗漏了结构性问题**：权威源自身失效、迁移登记断裂 2 个月、GET 触发 DDL

如按实测重估，问题面比 5/10 更广；但另一方面，**Drizzle 已有 131 个真实 FK 定义**（报告与既有认知都误认为为零），这部分比评价更乐观。

## 八、建议优先级

| 优先级 | 事项 | 理由 |
|---|---|---|
| **P0** | 把 i18n 文件中的 280 个 SQL 键还原为代码常量，删除合成键 | 唯一可以让"改翻译"变成"改 SQL"的通道 |
| **P0** | `/api/migrations` 移出 proxy 公开白名单 | 纵深防御补回一层 |
| **P0** | 把 `GET` 执行 DDL 改为 `POST` + 迁移登记 | 消除预取/扫描器误触发 |
| **P1** | 重建唯一权威 schema 源（重导全量 366 表 DDL），废除空的 `actual_schema.sql` | 三个"权威源"目前都不可信 |
| **P1** | 补齐 24 个未登记迁移，统一编号规范 | 迁移体系当前不可审计 |
| **P1** | 补齐 18 张有数据的未建模表（优先 `std_material` 4086 行） | 缺口真实影响业务 |
| **P2** | 退役 65 张 `_bak` 备份表或迁移到独立 schema | 占基表 17.8%，干扰所有覆盖率口径 |
| **P2** | 清理 3 张幽灵建模表 + 51 个含 DDL 的 scripts | 降低误用面 |
