### 3.0 为什么 approve 分支只做 SQL 级验证、不做 HTTP 实测

`SalesToWorkOrderHandler` **真建生产工单** —— 副作用无法保证清理干净。
故：

- **approve 分支** → 用「事务内执行 + 回滚」验证 SQL 与真实 schema 的兼容性（§一.4，`approve-sql-check.mjs`）；
- **PUT 端点** → 用**不入队任何事件、可 100% 还原**的 `reject` 动作做 HTTP 实测（上表 28–32）。

这是有意的取舍，已如实披露，不是遗漏。

#### 4.1.2 由测试暴露出的**代码**修正（不是改测试敷衍过去）

`tests/integration/workorder-api.test.ts` 的 `status: 'cancelled'` 用例暴露了一个**真实的健壮性缺口**：
`normalizeSalesOrderStatus` 只接受数字，而项目里**字符串状态是真实存在的取值来源** ——
`prod_work_order.status` 就是 varchar 状态机（pending/confirmed/producing/completed/cancelled），
领域 VO 的 `.value` 也是字符串，历史代码里确实写过 `status === 'cancelled'` 的比较。
若只认数字，`'cancelled'` 会被判为「未知」而**静默放行**，守卫永久失效 —— 正是 `BUG-ORD-002` 的同一类成因。

因此给 `src/lib/order-status.ts` 增加 `LEGACY_STRING_ALIASES`，并顺带修掉两个隐患：

1. `Number(true) === 1` → 布尔值会被误判成 `PENDING`；现显式挡掉 `typeof value === 'boolean'`。
2. `Number('2abc')` 之类会被截取；现字符串只接受**纯数字**（`/^\d+$/`）或显式别名。

`'rejected'` **刻意不收录**：销售订单的 reject 是「退回待确认」，不是取消。
