## 一、任务① `/hr/shifts` 「编辑班次 → 储存」失败

### 1.1 复现（修复前）

| 探针 | 结果 |
|---|---|
| `PUT /api/hr/shifts` 原样回写整行（含 `createTime`/`updateTime`） | **500** `{"message":"更新班次失败"}` |
| `PUT` 最小 body `{id, shiftName}` | 200 |
| 逐字段累加二分 | 前 13 个字段全 200；**加上 `createTime` 立刻 500** |

### 1.2 根因链（三段，逐段取证）

```
① src/lib/api-response.ts:17   sanitizeObject()
     if (obj instanceof Date) return obj.toISOString().slice(0, 10)
   → 所有 successResponse 出参里的 Date 被截成 'YYYY-MM-DD'，时分秒丢失
     实测：create_time '2026-07-23 16:44:15' → 出参 "2026-07-23"
② src/app/[locale]/hr/shifts/page.tsx:130  openEdit() → setForm(shift)
   → 表单直接持有接口返回的整行；保存时 handleSave() 提交 { id, ...form }
     （即把被截断的 createTime/updateTime 原样送回）
③ src/app/api/hr/shifts/route.ts:40  db.update(hrShift).set(body)
   → Drizzle 的 datetime 列在写入时执行 value.toISOString()，
     字符串没有该方法 → TypeError → 被 withPermission 包装成 500「更新班次失败」
```

**决定性实验**（`repro-shift-put2.mts`，全程在事务内执行后回滚）：

| patch | 结果 |
|---|---|
| J 完整 HTTP body（用户点保存时真实发送的内容） | **FAIL** `TypeError: value.toISOString is not a function` |
| G 仅 `{createTime: "2026-07-23"}` | FAIL 同上 |
| H 仅 `{updateTime: "2026-07-23"}` | FAIL 同上 |
| I 仅 `{createTime: "2026-07-23 16:44:15"}`（带时分秒字符串） | FAIL 同上 |
| K 完整 body 但**剔除** `createTime`/`updateTime` | **OK** |
| L 完整 body，两列换回 Date 对象 | **OK** |

⇒ 触发条件被精确锁定为「datetime 列收到**字符串**」，而字符串正是 `sanitizeObject` 造出来的。

### 1.3 修复（写入侧字段白名单）

`src/app/api/hr/shifts/route.ts`：新增 `SHIFT_WRITABLE_FIELDS` + `pickShiftWritable()`，
POST/PUT 只接受 12 个业务可写字段；`id`/`createTime`/`updateTime`/`deleted` 一律不接受客户端提交。
PUT 增加「无可更新字段 → 400」守卫（避免 Drizzle `.set({})` 抛 `No values to set`）。

设计取舍：

- **不改 `sanitizeObject`**：它对全站 `successResponse` 生效，改成完整 ISO 会波及所有页面已按 `YYYY-MM-DD` 展示的日期列（破坏兼容）。改为在**写入侧**拒绝审计字段——这本身就是"不信任客户端"的正确做法。
- **update_time 交由 DDL 维护**：`hr_shift.update_time` 带 `ON UPDATE CURRENT_TIMESTAMP`，不再由客户端覆盖。

### 1.4 连带发现并修复：同页「删除班次」也是坏的

页面发的是 `DELETE /api/hr/shifts?id=<id>`（**查询串、无 body**），
而路由读的是 `await request.json()` → 无 body 时抛异常 → 500「删除班次失败」。

实测证据：

| 调用方式 | 修复前 | 修复后 |
|---|---|---|
| `DELETE ?id=<id>`（页面实际用法，含批量删除） | **500** | **200** |
| `DELETE` + JSON body（路由原先期待的用法） | 200 | 200 |

修法：DELETE 的 id 改为**查询串优先、body 兜底**，并加 `Number.isInteger` 校验。

**影响面核实**：全仓库检索「DELETE handler 内读 `request.json()` 取 id」，只有 `hr/shifts` 命中；
另两处匹配（`warehouse/unit-conversion`、`system/oper-log`）的 `request.json()` 属其后的 PUT/POST，为误报。
⇒ 该契约不一致是**单点问题**，已收敛。

## 二、任务② `/settings/organization` 部门管理列表空白

### 2.1 根因（单点，已 100% 复现）

`src/app/[locale]/settings/organization/department-table.tsx` 的 `buildDepartmentTree()` 旧实现：

```ts
if (dept.parent_id === 0) { roots.push(node); }
else { const parent = deptMap.get(dept.parent_id); if (parent) { ... } }
```

而库里「顶级部门」的表示是 **`parent_id IS NULL`**，不是 0：

| `sys_department.parent_id` 实况（14 个存活部门） | 行数 |
|---|---|
| `IS NULL` | **12** |
| `= 97`（**父节点已软删**） | 2（模切车间、商标车间） |
| `= 0` | **0** |

⇒ `null === 0` 为 `false` → 12 个根部门全部落入 else 分支 → `deptMap.get(null)` 为 `undefined` →
**一个都不进 `roots`**；另外 2 个的父节点 97 已被 `deleted=0` 过滤掉 → 也不进 roots。
最终 `treeData = []` → 表格渲染「暂无部门数据」→ **列表空白**。

### 2.2 「现在部门是不是硬编码」——准确回答

**不是。** 部门数据来自真实表 `sys_department`，接口 `GET /api/organization/department` 实测返回
`total = 14`。空白不是"没有数据"，而是数据被前端树构建**静默丢弃**。

但页面里确实存在一处硬编码：`loadMockDepartments()` 内置 8 条假部门（`DEPT001`–`DEPT008`），
作为「接口失败 / 返回空」时的兜底。这本身是缺陷：

- 假数据的 `id` 与真实部门 **同域**（假 `id=1` 对应真 `管理部(1)`），
  用户若对「假部门」点编辑/删除，会**直接命中同 id 的真实部门**，造成脏写；
- 真实故障被假数据掩盖，看不到错误。

**已移除该兜底**，改为失败时 `toast.error(tc('fetchFailed'))`、空数据时表格显示「暂无部门数据」。

> 同一文件里 `loadMockCompany()` / `loadMockRoles()` 是同类兜底（本次未动，属同一模式，建议后续统一清理）。

### 2.3 连带发现（列出前全部实测取证）
