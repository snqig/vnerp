## 一、核心结论

1. **两份报告的缺陷方向基本正确，但定性有 4 处必须修正**（见第五节），其中生产工单的 2 个 P0 **在真实数据下不可复现为「未审核工单成功建单」**。
2. **根本原因比报告更严重**：`inv_production_inbound`、`prd_material_issue` 等 **8 张表的外键指向遗留表 `prd_work_order`**，而全部工单业务在 `prod_work_order`（两表 id 交集为 0）。→ **「工单 → 领料/入库/排程/成本」整条写入链路在数据层是断裂的**，任何传 `prod_work_order.id` 的写操作必然 `ER_NO_REFERENCED_ROW_2` → **500**。

4. **新发现 3 个报告未收录的缺陷，含 2 个 P0**（见第六节）：对账创建接口恒 500、退货单 `return_no` 未生成导致 409、`prod_work_order_item.material_id` 缺失。

## 五、与报告结论的差异（必须修正的 4 处）

### 5.1 生产 P0-1 / P0-2：现象描述不成立，机制需重写
- **报告原文**：「未审核（待生产）工单**可绕过校验直接创建完工入库单并过账**、可直接创建领料单，生产业务规则形同虚设。」
- **实测**：真实数据下**不可复现为「成功创建」**——`inv_production_inbound.work_order_id` FK 指向 `prd_work_order`，传 `prod_work_order.id` 必然 500。
- **正确表述**：
  1. 守卫确实失效（`'pending' < 20` → `false`，**代码与 JS 语义双证**），属**真实潜伏缺陷**；
  2. 但当前被 FK 错误掩盖，用户侧表现为 **500（接口完全不可用）**，而非越权成功；
  3. **一旦 FK 修正（或传入满足 FK 的 id），越权 100% 成立**（隔离实验已验证）；
  4. 因此真实的第一优先级应是 **NEW-P0-1（FK 指向遗留表）**，其次是守卫改写。
- 附：同一 bug 在**同一次修复中只改了 PUT 过账、漏了 POST 建单**（`production-inbound/route.ts` 头部已定义 `WO_STATUS` 字符串常量并在 PUT 使用，第 113 行 POST 仍写 `wo.status < 20`）。

### 5.2 采购 BUG-PUR-001：影响面比报告更大
- **报告原文**：「存量 44 条 status=2/3 读取降级为草稿，流转必然 409、状态筛选失真。」
- **实测补充**：不仅"失真"，**按状态筛选直接 500**——`?status=2`/`3` 返回 500，即**存量 44 条采购单在列表页按状态筛选中完全不可达**（`?status=all` 可返回 44 条）。`approve` 的错误文案"当前状态'草稿'不允许审核"**直接暴露降级事实**。

### 5.3 采购 CASE-008「对账幂等」：报告结论无法成立
- 报告把「对账单可重复创建」列为 P1。实测**两次创建都是 500**，即缺陷被 `NEW-P0-2` 完全阻断，**幂等问题当前不可观测**。应先把 `NEW-P0-2` 定为 P0 修复，再回归幂等。

### 5.4 采购 CASE-004「分单收货回写错配」：当前不可触发
- 库内**同单同物料多行的采购单数 = 0**，错配风险为**潜在**（匹配键确为 `material_code` 且忽略 `line_no`，代码级成立）。建议提升为"结构性风险"而非"已发生缺陷"。
