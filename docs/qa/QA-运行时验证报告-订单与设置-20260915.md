### 2.2 被证伪的 P0 详解（`BUG-SET-001`）

报告称：「变更记录表不存在，探测失败后容错逻辑把翻译文案当 SQL 执行（语法错误未捕获）→ 必然 500」。

复核事实：
1. 探测失败后的容错分支确实执行 `execute(ts('k_jyctof'))`（`system/route.ts:935`），但 **`k_jyctof` 的内容本身就是一段完整的 `CREATE TABLE IF NOT EXISTS sys_config_change_log (...) ENGINE=InnoDB ...` DDL**，被存放在 4 个语言包中（`zh-CN/en/zh-TW/vi` 全部存在该键）。
2. 因此这不是「翻译串误用」，而是**有意为之的「懒建表」实现**（把 DDL 当翻译资源存放）。运行时 `CREATE TABLE` 成功 → 随后的 `INSERT` 成功 → 接口返回 **200**。
3. 实测记录：`require_approval_for_config_change = "true"`、执行前 `sys_config_change_log` 不存在 → POST 返回 **200**「配置修改申请已提交，等待审批」→ 执行后该表已存在，变更记录 `{"config_key":"tax_rate","old_value":"13","new_value":"13","status":0}` 正确落库。

⇒ **P0 不成立**。但报告指向的设计问题是真的（见 2.3 建议）：生产运行时依赖 DDL 权限、schema 由翻译资源驱动、首次写入路径无事务保护。

### 2.4 报告结论中需要修正的表述

1. 「分类编码 179 条全部不合规」——口径不准。实际：物料分类 **169**（`category_code`，不叫 `code`）+ 仓库分类 **12**（表为 `sys_warehouse_category`，列名为 `code`）= **181** 条；其中 **2 条是合规的测试数据**（`WH-CAT-642571`、`WH-CAT-986553`）⇒ 不合规 **179** 条。数字巧合，但分母与表名都写错了。
2. 「仓库分类 10 条为 WHCAT001-010」——实为 12 条（10 条业务 + 2 条测试）。
3. 「`category_type` 列代码注释声称不存在」——列**确实存在**（报告已修正为 schema 漂移），但**169 行全为 NULL**，因此报告 OQ-004 的决议「回写直接读取该列」**不足以解决联动失准**：该列当前无任何有效数据，仍需以物料类型推断兜底。
4. `BUG-SET-002` 的「每次 GET 都可能 ALTER TABLE / 全量 UPDATE」在**代码层面成立**（`initDefaultConfigs → ensureConfigTableColumns + migrateOldConfigs + 逐键 upsert`，且 GET 无权限保护），但当前数据已收敛，连续 GET **未观测到任何行变化**（`update_time` 均未刷新——MySQL 在同值时跳过写入）。故应表述为「**读接口携带写路径与 DDL 权限要求**」，而非「每次 GET 都在写」。

### 3.1 修复验证证据

**审批闭环（`BUG-SET-005`）** —— 用低影响键 `a_class_cycle` 走完整闭环：

| 变更后 DB | **`a_class_cycle = "8"`, `update_time = 2026-09-15`** ⇒ ✅ 配置真正生效（修复前为静默不生效） |
| 清理 | 恢复 `a_class_cycle = "7"`，删除申请单，残留 0 |

**权限映射（`BUG-SET-011` / `NEW-SET-P1`）** —— 直接调用 `getRequiredPermission` 复核：

| 端点 | 方法 | 修复前 | 修复后 |
|---|---|---|---|
| `/api/settings/system` | GET / POST / PUT | `null`（无要求） | `system:config` |
| `/api/settings/change-approval` | GET / POST | `settings:approval` | `settings:approval` |
