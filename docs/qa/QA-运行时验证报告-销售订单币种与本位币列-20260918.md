- 结论：**现象属实，已修复并入 HEAD `ef455cf1`**；读接口映射漏字段 + 写接口不落币种/本位币 两处根因

## 1. 现象与定性

用户在 `http://localhost:5000/orders/sales` 提出：列表「币种」「本位币金额」两列不显示数据。

页面这两列的渲染逻辑（`src/app/[locale]/orders/sales/page.tsx:1271-1339`）：

```tsx
<TableHead className="text-right">{tc('currency')}</TableHead>      // 币种
<TableHead className="text-right">{t('baseAmount')}</TableHead>     // 本位币金额
...
{order.currency || <span className="text-muted-foreground">-</span>}
{order.base_total_amount != null
  ? <MoneyDisplay amount={order.base_total_amount} currency={order.base_currency || 'CNY'} />
  : <span className="text-muted-foreground">-</span>}
```

即：**字段取不到值就渲染 `-`**。列存在、表头正常，但单元格是 `-`。

## 2. 根因（三条运行时证据）

### 证据 A：接口根本没返回这些字段（修复前实测）

`GET /api/orders`（`src/app/api/orders/route.ts`）返回 35 条，首条字段清单为：

```
id, order_no, customer_id, customer_name, order_date, delivery_date,
status, total_amount, total_with_tax, items, remark, create_time, update_time
```

`currency` / `exchange_rate` / `base_currency` / `base_total_amount` / `base_tax_amount` / `base_grand_total` 全部 **`__ABSENT__`**（列表与详情分支**都**缺，二者是两段独立的返回映射）。查询是 `SELECT so.*`，数据其实取到了，**是在 JS 映射时被丢弃**。

### 证据 B：`sal_order` 真实列（`SHOW COLUMNS`，共 32 列）

| 列 | 类型 | 默认值 |
|---|---|---|
| `currency` | varchar(10) | CNY |
| `exchange_rate` | decimal(18,4) | 1.0000 |
| `base_total_amount` | decimal(18,4) | 0.0000 |
| `base_tax_amount` | decimal(18,4) | 0.0000 |
| `base_grand_total` | decimal(18,4) | 0.0000 |

**`base_currency` 列不存在** —— 本位币是系统级配置，不是订单属性。这解释了为什么代码里只能写成 `order.base_currency || 'CNY'`（恒为 undefined）。

### 证据 C：数据分布与写入侧缺口

- 35 行订单：`currency` 全为 `CNY`（取列默认值）、`exchange_rate` 全为 `1`（取列默认值）
- 其中 **15 行 `base_total_amount = 0` 且 `total_amount <> 0`**（其余 20 行 total_amount 本身为 0）
- `POST /api/orders` 的 INSERT 语句只写 `order_no / customer_id / order_date / delivery_date / total_amount / status / remark` —— **从不写 `currency`，也从不写 `base_*`**，所以新单的本位币快照恒为 0。

> 结论：这是一个「读映射漏字段」+「写未落值」的**双缺口**，单修任一侧都不够——只修读，历史 15 行仍是 0；只修写，已有 35 行依旧空白。

## 3. 修复清单（逐文件）

### `src/app/api/orders/route.ts`

1. **GET 列表 + 详情**：新增共用映射 `currencyFieldsOf(order)`，输出 6 个字段：
   `currency`（空则回落本位币）、`exchange_rate`、`base_currency`、`base_total_amount`、`base_tax_amount`、`base_grand_total`；
   列表与详情两处返回分别以 `...currencyFieldsOf(order)` 展开。
2. **本位币来源**：`getSystemConfig('finance.base_currency', 'CNY')`，与 `SalesApplicationService`（DDD 侧）**同一口径**，不新造真相源。
   - 实测 `sys_config` **无 `finance.base_currency` 键** → 恒回落 `CNY`（与 `finance.default_currency=CNY`、`sys_currency` 中 CNY 一致）。
   - `sal_order` 无 `base_currency` 列，故由配置派生后随行返回。
3. **POST 写入侧**：读取 `body.currency` → 落 `currency`；非本位币时经既有 `CurrencyApplicationService.getLatestRate(currency, baseCurrency)` 取汇率（缺失则 400，复用词条 `Common.k_uigql6`「未找到汇率记录」，不新增 i18n key）；按 `round(金额 × 汇率, 4)` 落 `exchange_rate / base_total_amount / base_tax_amount / base_grand_total`。
   - 税额口径：`base_tax_amount = round(max(total_with_tax − total_amount, 0) × rate, 4)`，**不做自动加税**，不改动 `total_with_tax` 既有语义。

### `database/migrations/084_backfill_sales_order_base_amounts.sql`（新增）

幂等存量回填（WHERE 命中一次后不再命中）：先把 `exchange_rate IS NULL` 归一为 1、空 `currency` 补 CNY；再分别回填 `base_total_amount`、`base_tax_amount`、`base_grand_total`。文件内附「迁移前留痕」与「迁移后自检」两条 SELECT。

## 7. 新发现（含「未动」与「为什么不动」）

| # | 发现 | 证据 | 处置 |
|---|---|---|---|
| 1 | `MysqlSalesOrderRepository.save()` 的 INSERT 写了 `sal_order` **不存在的列**：`customer_name / total_qty / shipped_qty / warehouse_id` | `SHOW COLUMNS FROM sal_order` 32 列中无这些列；而 `SalesOrderRow` 接口却把它们当既有列 | **未动**。属「DDD 仓储层 vs 真实 schema」的系统性偏差，一旦 `REPOSITORY_IMPL=drizzle` 或走 DDD 创建路径必 500。改动面涉及聚合根字段与迁移，需单独排期 |
| 2 | `sal_order` 无 `base_currency` 列 | 同上 | 本次按「配置派生」实现（与 DDD 侧一致）；若未来需要「订单级本位币快照」需另加迁移 |
| 3 | `/api/orders` 与 `/api/orders/sales` 双入口，逻辑与字段集合不同 | `sales/route.ts` 无业务页面调用，仅 `tests/e2e/production-workflow.spec.ts:61` 引用；项目内已有「双入口保留其一」待决记录 | **未动**。属产品入口归属决策，删改需先确认 |
| 4 | **核实**报告称「`std_material.unit_cost` 全 NULL（4086 行）」 | `SELECT COUNT(*), SUM(unit_cost IS NULL) FROM std_material` → total=4086, nul=4086 | **属实**。未动（成本口径需业务确认） |
| 5 | **核实**报告称「分切白名单未实现，网版/油墨/刀模仍可分切」 | 机制**存在**：`inv_material.is_splittable` + `assertMaterialSplittable()`，接线在 `/api/warehouse/split-order` 两处（:110、:236）。但数据上 `is_splittable=1` 的 784 个物料**全部落在 `category_id=1`**，其中「网版」类物料（`material_name='网版'`）确为 `1` → **「网版仍可分切」属实**；油墨/感光胶（category_id=2）为 `0`，符合预期 | **未动**。「网版应否可分切」是业务规则，需确认白名单分类口径后再改数据 |
| 6 | `inv_inventory_batch` **无** `is_splittable` 列，但拆分页读取 `batch.is_splittable` | `SHOW COLUMNS FROM inv_inventory_batch` 无该列 | **待确认**：需查批次查询是否 JOIN `inv_material` 提供该字段；若是纯读 batch 行则该判断恒 false，会误禁用创建。属 P1 候选 |
